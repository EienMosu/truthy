Contradiction: the same page says customer-managed failover is not supported for either account in an object replication policy, while its feature table marks object replication as supported for unplanned failover: write no card on object replication and failover. Cosmos DB continuous backup has 7-day, 30-day and 35-day tiers; much study material lists only 7 and 30, so no card may claim only two tiers; continuous backup does not support the API for Cassandra; backups are not automatically geo-disaster resistant, and another region must be added (https://learn.microsoft.com/en-us/azure/cosmos-db/continuous-backup-restore-introduction). That page says both that deleted containers and databases can be restored into an existing account and that "the restore action always restores data into a new account": write no card on the target account of a Cosmos DB restore. Azure SQL Database point-in-time restore retention (1 to 35 days, 7 by default) and long-term retention (up to 10 years) are numbers: avoid them or set "volatility": "may_change".
- High availability traps (3.2), verified on failover-group-sql-db: a failover group's read-write and read-only listener endpoints stay the same after a geo-failover, so the connection string does not change; a planned failover synchronizes fully and loses no data, a forced failover can lose data; Microsoft-managed failover applies to all failover groups in the region that use that policy, after a grace period that cannot be set below one hour; secondaries created by a failover group do not get zone redundancy by default except in Hyperscale, where they inherit the primary's setting; multiple secondaries per failover group are Preview, so write no card that a failover group supports only one secondary or several. Contradiction: the page says the secondary cannot be in the primary's region, while its Preview multiple-secondaries section allows the same or a different region: write no card on the region of a failover group secondary. Failover groups for Azure SQL Managed Instance have their own page: any Managed Instance card cites it. Recovery figures (geo-failover RTO typically under 60 seconds, zone-redundant HA RTO typically under 30 seconds with RPO 0, per https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview) are numbers: avoid them or set "volatility": "may_change".
- Compute traps (4.1), verified on functions-scale, https://learn.microsoft.com/en-us/azure/azure-functions/consumption-plan, https://learn.microsoft.com/en-us/azure/azure-functions/flex-consumption-plan and compute-decision-tree: the Consumption plan is legacy (Windows GA; hosting on Linux in a Consumption plan retires on September 30, 2028 and gets no new features or language versions, while the functions-scale table already marks Linux Consumption as retired), so no card presents Linux Consumption as an option for new apps and no card hinges on its retirement status; Flex Consumption runs on Linux only, supports no containers, supports virtual network integration and always ready instances and can scale to zero; Premium keeps at least one instance warm, supports Linux containers and virtual network integration; an HTTP-triggered function must respond within 230 seconds whatever the timeout setting, which is why the async pattern of Durable Functions exists. Azure Container Apps gives no direct access to the Kubernetes API, while AKS does; Azure Container Instances gives no full orchestration; every compute platform in the decision guide is regional and needs an external router for multi-region designs. Azure Batch has no extra charge beyond the resources it uses, and Microsoft points to Azure CycleCloud when a specific scheduler or existing on-premises workflow must be kept (https://learn.microsoft.com/en-us/azure/batch/batch-technical-overview). Instance, node and core limits in these pages are numbers: avoid them.
- Application architecture traps (4.2), verified on https://learn.microsoft.com/en-us/azure/service-bus-messaging/compare-messaging-services and https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-azure-and-service-bus-queues-compared-contrasted: Event Grid routes discrete events, Event Hubs ingests time-ordered event streams with per-partition ordering, consumer groups and Capture, and Service Bus brokers high-value messages with transactions, duplicate detection, dead-lettering and FIFO through sessions; Event Hubs has no dead-lettering and no duplicate detection. Storage queues fit a backlog larger than 80 GB and server-side transaction logs, and they have no ordering guarantee; Service Bus queues support long polling, sessions, At-Most-Once through ReceiveAndDelete and AMQP 1.0. The comparison table writes "exactly once with sessions" for Service Bus while the queue comparison page says the term "isn't exactly adequate": write no exactly-once card. Message and queue size limits are numbers: avoid them. API Management, verified on https://learn.microsoft.com/en-us/azure/api-management/api-management-features: virtual network injection exists in Developer, Premium and Premium v2; multi-region deployment only in Premium; availability zones in Premium and Premium v2; the self-hosted gateway in Developer and Premium; Developer has no SLA and is for non-production; Consumption has no built-in cache. Test tiers only with the tier named in the statement and set "volatility": "may_change" (v2 tiers are still gaining features). Azure Managed Redis is clustered by default, zone-redundant by default and built for Microsoft Entra ID authentication, but it also offers non-high-availability options for dev/test, so no card may say every instance is highly available; caching cards use Azure Managed Redis, not Azure Cache for Redis.
- Migration traps (4.3): the Cloud Adoption Framework now lists seven phases, Strategy, Plan, Ready, Adopt, Govern, Secure and Manage, with Adopt covering migrate, modernize and build (https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/overview); older material names Define strategy, Innovate or separate Migrate and Innovate methodologies: no card may use the old list. - Network traps (4.4), verified on https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/load-balancing-overview: Azure Front Door is global and HTTP(S) with caching and acceleration; Traffic Manager is global and DNS-based, balances only at the domain level and fails over more slowly than Front Door because of DNS caching; Application Gateway is regional; Azure Load Balancer is layer 4, zone-redundant, and has regional and cross-region topologies; API Management is not a general-purpose load balancer. Application Gateway layer 4 (TCP and TLS proxy): its page showed no Preview label on 2026-10-08; write a card on it only if https://learn.microsoft.com/en-us/azure/application-gateway/tcp-tls-proxy-overview still shows it as generally available. ExpressRoute traffic does not cross the public internet; the Premium add-on extends connectivity across geopolitical regions; Global Reach links on-premises sites through their circuits; the Local SKU includes data transfer in the port charge; write no card on whether ExpressRoute traffic is encrypted by default. VPN Gateway: Basic supports no BGP, no RADIUS and no IKEv2 or OpenVPN point-to-site, and a new gateway needs a Standard public IP; more than 100 site-to-site tunnels point to Virtual WAN. Private endpoints: a network interface with a private IP from the virtual network, reachable from peered virtual networks and from on-premises over VPN or ExpressRoute, deployed in the same region and subscription as its virtual network while the target resource may be in another region, needing DNS that resolves to the private IP, and not by itself restricting public network access to the service (private-endpoint-overview). Service endpoints are enabled per subnet, let private addresses reach a service without public IPs, cannot be used for traffic from on-premises, and for Azure SQL apply only within the virtual network's region (https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview). Azure Firewall has Basic, Standard and Premium SKUs, and TLS inspection and malware protection are Premium features (https://learn.microsoft.com/en-us/azure/firewall/choose-firewall-sku); Azure DDoS Protection has two tiers, DDoS IP Protection and DDoS Network Protection (https://learn.microsoft.com/en-us/azure/ddos-protection/ddos-protection-sku-comparison).
