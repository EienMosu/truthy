RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: foundational, for a technology professional starting with Azure. Test defined terms, what each Azure service or feature named in the guide is for, its scope (resource, resource group, subscription, management group; region, availability zone, global), and the distinction between two similar options: availability sets versus availability zones, Azure VPN Gateway versus ExpressRoute, private endpoints versus public endpoints, LRS, ZRS, GRS and GZRS, the hot, cool, cold and archive tiers, AzCopy versus Azure Storage Explorer versus Azure File Sync, Azure Migrate versus Azure Data Box, Microsoft Entra ID versus Microsoft Entra Domain Services, authentication versus authorization (MFA and Conditional Access versus Azure RBAC), Azure Policy versus Azure RBAC versus resource locks, Azure Advisor versus Azure Service Health versus Azure Monitor. Stay inside the services and concepts the guide's bullets name; no configuration steps, command syntax, SKUs or portal navigation. The guide names no Azure AI service: write no AI cards.
- Skill area 1 is vendor-neutral and overlaps the AWS Cloud Practitioner and Google Cloud Digital Leader decks. It is also the easiest place to write truisms ("the cloud lets you scale"). Anchor every card in how Microsoft Learn defines the term: who is responsible for what under IaaS, PaaS and SaaS in the shared responsibility model, CapEx versus OpEx, the consumption-based model, serverless, vertical versus horizontal scaling, elasticity, reliability versus predictability, and Microsoft's own wording for the use cases of each cloud model and service type.
- Never state a judgement as a fact. "X is the best option" is acceptable only when the statement contains the full requirement that makes it so and Microsoft documentation supports it. Prefer statements about behaviour and purpose. Trap: availability sets are current, but Microsoft now recommends Virtual Machine Scale Sets with flexible orchestration for high availability and states that availability sets give less resiliency than availability zones; no card may present availability sets as the recommended option.
- Renamed products: use today's names exactly: Microsoft Entra ID (formerly Azure Active Directory), Microsoft Entra Domain Services, Microsoft Entra Conditional Access, Microsoft Entra multifactor authentication, Microsoft Entra External ID, Microsoft Defender for Cloud, Microsoft Purview, Microsoft Cost Management, Azure Monitor Application Insights, and, for sovereign regions, Azure Government and Microsoft Azure operated by 21Vianet. Renames are not knowledge: no "X was formerly called Y" cards, and never make a statement false by using an old name.
- Leave out retired, retiring or closed products and features: Azure Blueprints (Preview; phased retirement since July 31, 2026, retired January 31, 2027; Microsoft points to deployment stacks and template specs), Azure AD B2C (no longer available to purchase for new customers since May 1, 2025; external identities cards use Microsoft Entra External ID), Azure Data Box Heavy (retired) and the 80 TB Data Box device (being retired region by region as the 120 TB and 525 TB next-generation devices arrive, so no capacity cards), the classic deployment model and classic storage accounts (retired August 31, 2024), general-purpose v1 and legacy Blob Storage accounts (retired or scheduled for retirement; Standard general-purpose v2 is the account type to test), and the Azure TCO calculator (no longer in the study guide; its old page now redirects to a blog post). Cost cards use the pricing calculator and Microsoft Cost Management.
- Changed defaults and counts that are traps here: not every Azure region has a pair, many newer regions are nonpaired, some pairs are asymmetrical, you cannot choose your own pair, and Microsoft states that deploying to a paired region gives no automatic high availability, disaster recovery or failover by itself. Not every region has availability zones; a region that has them has at least three, some have more, and a zone is one or more datacenters with independent power, cooling and networking: test what a zone is and that it is "at least three", never an exact count. New virtual networks created with API versions released after March 31, 2026 get private subnets by default (the portal already did), so write no card on default outbound internet access for VMs. Blob Storage now also has a smart tier (generally available in public cloud regions with zone-redundant accounts; it moves data between hot, cool and cold and does not use archive), so no card may claim a fixed list of exactly three or four tiers. The archive tier works only with LRS, GRS and RA-GRS accounts; if you test this, set "volatility" to "may_change". The minimum storage durations of the cool, cold and archive tiers (30, 90, 180 days), licensing (Conditional Access needs Microsoft Entra ID P1), fault and update domain counts and numeric SLAs are packaging or numbers: avoid them, or set "volatility" to "may_change".
- Overlap with the decks written in parallel: containers belong to docker-fundamentals and kubernetes-kcna, infrastructure as code to terraform-associate, Zero Trust and authentication methods also appear in web-security, and Azure developer depth belongs to no deck here. In this deck such cards must rest on how Azure or Microsoft offers or defines the concept (Azure Container Instances, Azure Container Apps, Azure Kubernetes Service, App Service, Azure Functions; ARM templates and Bicep through Azure Resource Manager; the three Zero Trust principles verify explicitly, use least privilege and assume breach, and the defense-in-depth layers as Microsoft Learn lists them), not on generic container, Terraform or security knowledge.
- Lock names differ by tool: the portal calls them Delete and Read-only, the command line CanNotDelete and ReadOnly. Use the portal names unless the statement says which tool it means. Locks apply to control plane operations, not data plane operations, and apply to all users and roles; you cannot add a lock to a management group.
