STEP 2. Plan the whole deck before writing any card
For every section, list the 12 facts its cards will test, each as a short factKey (kebab-case, for example "ebs-volume-single-az"). The plan must satisfy:

- No mirrored pairs (service A wrongly given B's job in one card, and B wrongly given A's job in another). Pick one side.
- No repeated distractor template. If one card is false because "X is described as a firewall", no other card may use that same trick with a different X.

- Half of each section's cards are true and half are false.
Put the plan in the "plan" field of batch b1. In later batches you may deviate from the plan only to fix a problem, and then say so in "notes".

RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: associate level, for a hands-on engineer who runs workloads on Google Cloud. Test behaviour and configuration: what a resource or setting does, its scope (global, regional, zonal; organization, folder, project), how inheritance works, which product, feature or command group carries out a stated task, and how two similar options differ. Assume the player already knows what each product is for; cards that only identify a product belong to the Cloud Digital Leader deck.
- Command-line cards are welcome when they test which tool or command group does a task (gcloud, gcloud storage, bq, kubectl). Do not test exact flag spellings or output formats. gsutil is a legacy, minimally maintained CLI and Google recommends gcloud storage; never present gsutil as the recommended tool.
- Never state a judgement as a fact. "X is the best choice" or "X is the most cost-effective option" is acceptable only when the statement contains the full requirement that makes it so and Google Cloud documentation supports it. Prefer statements about behaviour.
- Renamed products are the main trap of this guide. Use the names the guide and the official rename page use today: Gemini Enterprise Agent Platform (formerly Vertex AI Platform), Agent Runtime on Gemini Enterprise Agent Platform (formerly Vertex AI Agent Engine), Gemini Enterprise Agent Platform Workbench (formerly Vertex AI Workbench), Cloud Run functions (formerly Cloud Functions), Google Cloud Observability (formerly Stackdriver), Workload Identity Federation for GKE. A card may mention a former name only to test that the rename happened, at most once in the whole deck.
- Cloud Run functions is the former Cloud Functions (2nd gen); the original generation is now called Cloud Run functions (1st gen). Cards about functions test current Cloud Run functions behaviour, never 1st gen specifics, and never present 1st gen as the default.
- Retired or legacy features: Container Registry is shut down (Artifact Registry replaces it; gcr.io URLs hosted on Artifact Registry keep working) and Deployment Manager reached end of support on March 31, 2026 (Infrastructure Manager, also written Infra Manager, replaces it): do not test them except as the replaced side of a single card. Preemptible VMs still exist but Google recommends Spot VMs, and the 24-hour maximum runtime applies to preemptible VMs, not to Spot VMs; keep these two straight. Test the Ops Agent, not the legacy Logging agent or Monitoring agent.
- Similar names that are easy to swap: Workforce Identity Federation (1.1, external users) versus Workload Identity Federation (4.2, external workloads) versus Workload Identity Federation for GKE (4.2, GKE workloads using IAM); network tags (VPC firewall rules only) versus secure Tags (Cloud NGFW firewall policies only); zonal Persistent Disk, regional Persistent Disk and Hyperdisk; GKE Autopilot versus Standard; Cloud Run versus Cloud Run functions. Test each pair once, from one side, never as a mirrored pair.
- Avoid overlap inside this deck: IAM role granting mechanics in 1.1 stay at project level; role types, custom roles and inheritance in the hierarchy belong to 4.1. Firewall rule creation and rule attributes belong to 2.3; 3.3 tests subnet range expansion, static IP reservation, custom static routes, Cloud DNS and Cloud NAT, with at most two firewall cards. Choosing and deploying compute belongs to 2.1; operating it (snapshots, node pools, autoscaling, traffic splitting) belongs to 3.1. Choosing data and storage products belongs to 2.2; backups, lifecycle rules, queries and CMEK belong to 3.2.
- Avoid overlap with other decks: generic Kubernetes object behaviour belongs to the Kubernetes deck (kubernetes-kcna), so GKE cards, including the Pods, Services, StatefulSets and Pod autoscaling bullets of 3.1, test GKE-specific behaviour (Autopilot and its Pod resource requests, node pools and node pool autoscaling, regional and private clusters, Artifact Registry access, Workload Identity Federation for GKE). Terraform language belongs to terraform-associate, so tooling cards in 2.4 test Google Cloud specifics (Config Connector, Fabric FAST, Application Design Center, Helm on GKE), not HCL syntax. Cloud Run and Cloud Run functions container details stay on the Google Cloud side (docker-fundamentals covers images). No comparisons with AWS or Azure services.
- AI-assisted tooling (1.1, 2.4, 3.2, 3.4) changes fast and has mixed launch stages. Application Design Center and Cloud Hub are generally available, but some of their features are Preview (for example Cloud Hub App Topology, and Database Center support for self-managed databases on Compute Engine VMs). Gemini Cloud Assist is documented on its overview page as a Preview offering: write at most three Gemini Cloud Assist cards in the whole deck, only about what that overview page states it does, and none about features marked Private Preview. Gemini CLI: test it as Google Cloud documents it (open source, available in Cloud Shell, quotas from Gemini Code Assist editions); do not test consumer plans or tiers (Gemini CLI was replaced by Antigravity CLI for unpaid and Google One users on June 18, 2026). For every card on these tools use the exact current product name, set "volatility" to "may_change", and leave out any feature marked Preview.
- Cost cards (1.2 budgets, 3.2 estimating storage costs) test cost mechanisms (budgets alert but do not cap spending, billing export destinations, the cost dimensions of storage classes, minimum storage durations), never prices. Cards about GKE or Compute Engine defaults that depend on version or machine series set "volatility" to "may_change".
