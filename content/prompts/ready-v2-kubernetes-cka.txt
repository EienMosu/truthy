- Scope of 1.1 Implement storage classes and dynamic volume provisioning (the administrator who creates the classes):
  - StorageClass provisioner, parameters, reclaimPolicy (Delete when unset), allowVolumeExpansion and mountOptions. Mount options are not validated: an invalid option makes the mount fail, and a plugin that does not support mount options makes provisioning fail.
  - volumeBindingMode: Immediate (the default) versus WaitForFirstConsumer, which delays binding and provisioning until a Pod that uses the PVC is created and honours the Pod's scheduling constraints. A Pod that sets nodeName bypasses the scheduler and leaves such a PVC Pending.
  - allowedTopologies.
  - Marking a default class with the storageclass.kubernetes.io/is-default-class annotation; when several classes are marked, the most recently created default is used.
  - Dynamically provisioned PVs take the reclaim policy of their class.
  - Local volumes have no dynamic provisioning in v1.35 and use WaitForFirstConsumer.
  - Volume expansion can only grow a volume, and it needs support from the volume plugin or CSI driver as well as allowVolumeExpansion.
  - VolumeAttributesClass (stable since v1.34) changes attributes of an existing CSI volume whose driver implements ModifyVolume.
  - VolumeSnapshot, VolumeSnapshotContent and VolumeSnapshotClass are CRDs, not part of the core API, and work only with CSI drivers; they need the snapshot controller and CRDs installed. At most one snapshot card.

- Scope of 1.2 Volume types, access modes, reclaim policies, PVs and PVCs (the administrator side of the PV lifecycle):

  - The phases Available, Bound, Released and Failed. The page also shows Pending for newly created volumes, so write no card claiming a fixed number of phases.

  - With Retain, a deleted PVC leaves its PV Released and unavailable to new claims until an administrator reclaims it. Deleting the PV leaves the storage asset in place.
  - Pre-binding with volumeName on the PVC, and reserving a PV with claimRef. Pre-binding ignores node affinity but still checks storage class, access modes and size.
  - Changing a PV's reclaim policy by patching it.

  - volumeMode Filesystem versus Block.
  - hostPath PVs are for single-node testing only; local PVs need nodeAffinity.

  - Mirror Pods: deleting a mirror Pod through the API does not stop the static Pod. A static Pod spec cannot refer to other API objects such as ServiceAccounts, ConfigMaps or Secrets.

    - no kube-controller-manager: controllers stop reconciling, so a new Deployment gets no ReplicaSet or Pods;
    - no kube-apiserver: kubectl fails, while running containers keep running;

  - Using crictl on the node when the API server is unavailable.
  - The kubelet and container runtime log to journald on systemd nodes, while static Pod container logs sit under /var/log/pods.

- Scope of 2.4 Manage and evaluate container output streams (the node and cluster side of logs):

  - The kubelet rotates container logs under containerLogMaxSize and containerLogMaxFiles (no numbers).
  - kubectl logs is served by the kubelet reading the log file, and only the latest log file is available after rotation.
  - By default the kubelet keeps one terminated container with its logs after a restart, and logs are removed when a Pod is evicted from the node.

  - CoreDNS Pods staying Pending until a Pod network add-on is installed, which the kubeadm troubleshooting page calls expected by design, versus CoreDNS Pods failing after the add-on is installed, which points to a broken network add-on.
  - CoreDNS failures from the dns-debugging-resolution page:
    - checking the CoreDNS Pods with the k8s-app=kube-dns label and their logs;
    - the kube-dns Service and its EndpointSlices;
    - adding the log plugin;
    - CoreDNS needing list and watch permissions on Services and EndpointSlices;
    - a forwarding loop when the node's resolv.conf points at a local stub such as systemd-resolved, fixed with the kubelet's resolv-conf setting, which kubeadm detects automatically.
  - Pod network ranges that overlap host networks.
  - NetworkPolicy as a cause of blocked traffic.
  - Ownership: CKAD owns the application-level debug-service steps (does the Service exist, does its selector match ready Pods, short names and namespaces). Write no card that only restates those steps. Configuring CoreDNS belongs to 5.2.
- Scope of 3.1 Rollouts, ConfigMaps and Secrets, and autoscaling (about two cards on rollouts, two on Secrets and six on autoscaling).
  - Rollouts, for the workloads administrators run as cluster components:
    - DaemonSet RollingUpdate (the default) versus OnDelete;
    - StatefulSet RollingUpdate with a partition (only Pods with an ordinal at or above the partition are updated when the template changes) versus OnDelete;
    - kubectl rollout undo for DaemonSets (rollback-daemon-set page).
    CKAD owns Deployment rollout mechanics, and StatefulSet maxUnavailable is beta in v1.35 (no cards).
  - Secrets, as the API server stores them:
    - encryption at rest configured through an EncryptionConfiguration passed to kube-apiserver with --encryption-provider-config;
    - the first provider encrypts new writes, and when reading, each provider that matches the stored data tries in order to decrypt;
    - identity stores plain text and is the default;
    - existing Secrets are not encrypted until they are rewritten, for example with kubectl replace.
    KMS v1 is deprecated since v1.28, and the docs mark aescbc and aesgcm as not recommended (aesgcm except with automated key rotation): no card presents any of them as recommended. CKAD owns consuming ConfigMaps and Secrets in Pods; KCNA owns the fact that Secrets are not encrypted at rest unless configured.
  - Autoscaling:
    - the HorizontalPodAutoscaler controller runs in kube-controller-manager and reads the resource metrics API (needs metrics-server) or the custom and external metrics APIs;
    - utilization targets are computed against requests, so when some containers lack the relevant request, utilization is undefined and the HPA takes no action for that metric;
    - autoscaling/v2 with multiple metrics, where the largest proposed replica count wins, and container resource metrics (stable since v1.30);
    - scale-down stabilization and the behavior field, without numbers;
    - the HPA manages the target's replicas, so the docs recommend removing spec.replicas from the Deployment or StatefulSet manifest;
    - the VerticalPodAutoscaler and node autoscaling are separate add-ons, not part of the core control plane.
    HPAConfigurableTolerance is beta in v1.35 and HPA scale to zero is alpha: write no card on the tolerance value or on minReplicas 0. In-place Pod resize (stable since v1.35) belongs to CKAD.
- Scope of 3.2 Self-healing primitives, and Pod admission and scheduling.
  - Self-healing:
    - voluntary versus involuntary disruptions;
    - PodDisruptionBudgets limit only voluntary disruptions that go through the Eviction API (kubectl drain uses it), while deleting Pods or Deployments directly bypasses them;
    - involuntary disruptions cannot be prevented by a PDB but count against the budget;
    - workload rolling updates are not limited by PDBs;
    - the docs recommend the AlwaysAllow unhealthy Pod eviction policy so that misbehaving applications can be evicted during a node drain;
    - the Eviction API answers 429 Too Many Requests when a budget would be violated.
  - Scheduling:
    - node affinity required versus preferred, and the meaning of IgnoredDuringExecution;
    - when both nodeSelector and nodeAffinity are set, both must be satisfied; several nodeSelectorTerms are ORed, and the matchExpressions in one term are ANDed;
    - the taint effects NoSchedule, PreferNoSchedule and NoExecute, and tolerationSeconds;
    - node-restriction.kubernetes.io/ labels for workload isolation with NodeRestriction;
    - nodeName bypassing the scheduler;
    - PriorityClass and globalDefault (only one allowed), preemptionPolicy Never, and the built-in system-cluster-critical and system-node-critical classes;
    - preemption gives victims their graceful termination period, and PDBs are respected only on a best-effort basis during preemption;
    - topology spread constraints (whenUnsatisfiable, and maxSkew as a concept with no numbers).
    The control-plane taint is a 4.2 fact.
  - Admission: LimitRanger, ResourceQuota and the order authentication, authorization, admission are owned by CKAD 4.1 and 4.2. Here, at most one admission card, about NodeRestriction limiting what a kubelet can modify (kubeadm enables it).
  - Ownership: KCNA owns the definitions of affinity, taints, priority and topology spread.
  - Numeric toleration operators (Gt and Lt) are alpha since v1.35: write no card claiming that tolerations support only Equal and Exists.
- Scope of 4.1 Manage role based access control:
  - ClusterRoles for cluster-scoped resources (nodes, PersistentVolumes, namespaces) and non-resource URLs; only a ClusterRoleBinding grants them cluster-wide.
  - roleRef is immutable, so changing the role of a binding means deleting and recreating it (kubectl auth reconcile handles that).
  - Privilege escalation prevention, which is enforced at the API level even without the RBAC authorizer:
    - you can create or update a Role only with permissions you already hold at that scope, unless you have the escalate verb;
    - you can bind a role only if you hold its permissions or have the bind verb.
  - Aggregated ClusterRoles: the control plane fills in their rules from labelled ClusterRoles and overwrites manual edits. The default admin, edit and view roles are extended through aggregate-to-* labels.
  - The default user-facing roles cluster-admin, admin, edit and view: view does not allow reading Secrets, and edit does not allow viewing or changing Roles and RoleBindings.
  - Auto-reconciliation of default roles and bindings at every API server start-up, disabled per object with the rbac.authorization.kubernetes.io/autoupdate annotation set to false.
  - Subresources such as pods/log and pods/exec.
  - resourceNames limits:
    - resourceNames cannot restrict deletecollection or top-level create (subresources such as pods/exec can be restricted);
    - list and watch can be restricted by resourceNames only when the client sends a metadata.name field selector.
    Popular material says list and watch cannot be restricted by name; on the v1.35 page they can, so write no card claiming they cannot.
  - Users are identities from client certificates (CN is the user name, O fields are the groups) or tokens, not API objects.
  - The CertificateSigningRequest API with the kubernetes.io/kube-apiserver-client signer and kubectl certificate approve for issuing user certificates; kubeadm kubeconfig user.
  - The ServiceAccount user and group name prefixes (system:serviceaccount:<namespace>:<name>, system:serviceaccounts:<namespace>).
  - kubeadm's admin.conf certificate is in the kubeadm:cluster-admins group, which is bound to cluster-admin. super-admin.conf is in system:masters, a break-glass group that bypasses the authorization layer.
  - Ownership: CKAD owns additive permissions with no deny rules, Role versus RoleBinding scope, a RoleBinding that references a ClusterRole, granting a ServiceAccount permissions and kubectl auth can-i --as; KCNA owns the RBAC object names.
- Scope of 4.2 Infrastructure preparation and kubeadm:
  - Host prerequisites:
    - unique hostname, MAC address and product_uuid;
    - required ports open;
    - net.ipv4.ip_forward enabled;
    - a CRI runtime installed;
    - by default the kubelet fails to start when swap is detected, unless it is configured to tolerate swap.
  - kubeadm detects the runtime from known sockets and asks you to specify one when it finds several or none.
  - Docker Engine needs cri-dockerd because it does not implement the CRI.
  - The docs recommend the systemd cgroup driver when systemd is the init system and with cgroup v2. Cgroup driver trap: the kubelet's own default is cgroupfs, while kubeadm sets systemd when cgroupDriver is unset. Since v1.34 the kubelet takes the driver from a runtime that supports the RuntimeConfig CRI call (KubeletCgroupDriverFromCRI, GA), and v1.35 still falls back to its own setting for older runtimes such as containerd 1.x. The current docs no longer carry the v1.35 warning that mismatched drivers make the kubelet fail. Write no card on which setting wins and none claiming that mismatched drivers make the kubelet fail.
  - kubeadm does not install or manage the kubelet or kubectl, and the kubelet restarts in a crashloop until kubeadm init or join tells it what to do.
  - What kubeadm init sets up: certificates in /etc/kubernetes/pki, kubeconfig files, static Pod manifests, a local etcd member, the CoreDNS and kube-proxy add-ons, the node-role.kubernetes.io/control-plane:NoSchedule taint (one card in the deck), and a bootstrap token.
  - CoreDNS does not start before a Pod network add-on is installed. A cluster can have only one Pod network, and the Pod network range must not overlap host networks.
  - Joining worker nodes with a bootstrap token and the discovery CA certificate hash, and kubeadm token create --print-join-command for a new join command.
  - Certificate management:
    - kubeadm renews all the certificates it manages during a control plane upgrade (opt out with --certificate-renewal=false);
    - kubeadm certs renew must run on every control plane node and needs a restart of the control plane Pods;
    - kubeadm configures the kubelet client certificate for automatic rotation;
    - kubeadm does not support rotating or replacing the CA out of the box.
  - kubeadm reset does not clean up iptables rules or IPVS tables.
  - kubeadm offers no automated way to reconfigure components on existing nodes: changes are made by editing the kubeadm ConfigMaps and the files on disk (kubeadm-reconfigure page).
  - The install-kubeadm page still says only one minor version of skew between the kubelet and the control plane is supported: skew cards cite the version skew policy (4.3), never that sentence.
  - Swap support (NodeSwap) is GA since v1.34 with NoSwap as the default swap behaviour, while the kubeadm upgrade page says swap must be disabled: write no card claiming that Kubernetes does not support swap.
  - cgroup v1 trap: the v1.35 release announcement is headed "Removal of cgroup v1 support", but the v1.35 docs say cgroup v1 is deprecated and that the kubelet will not start on a cgroup v1 node by default (failCgroupV1 defaults to true and can be set to false). Test only "fails to start by default", never that support is fully removed.
  - v1.35 is the last release to support containerd 1.x: no card on containerd versions.
- Scope of 4.3 Cluster lifecycle, etcd backup and restore, and a highly available control plane. The 2025 curriculum no longer names etcd backup and restore, so give etcd at most three cards.
  - Upgrades:
    - skipping minor versions is unsupported;
    - the high-level order is the primary control plane node (kubeadm upgrade plan, then kubeadm upgrade apply), the other control plane nodes (kubeadm upgrade node), then the worker nodes (kubeadm upgrade node, which upgrades the kubelet configuration);
    - kubeadm is upgraded first, and the kubelet and kubectl separately with the package manager, followed by a kubelet restart;
    - a node must be drained before a minor upgrade of its kubelet and uncordoned afterwards;
    - since v1.28, kubeadm upgrades CoreDNS and kube-proxy only after all control plane instances are upgraded;
    - the administrator upgrades the CNI plugin manually;
    - kubeadm writes backups of the etcd data and static Pod manifests under /etc/kubernetes/tmp;
    - the community package repositories at pkgs.k8s.io have a dedicated repository per minor version, so a minor upgrade needs the repository changed, and the legacy apt.kubernetes.io and yum.kubernetes.io repositories are frozen since September 13, 2023.
    Upgrade trap: the same upgrade page says "kubeadm upgrade does not touch your workloads" and "All containers are restarted after upgrade, because the container spec hash value is changed". Write no card claiming that a kubeadm upgrade leaves every running container untouched.
  - Version skew (version-skew-policy page):
    - kube-apiserver instances in an HA cluster are within one minor version of each other;
    - the kubelet and kube-proxy are never newer than kube-apiserver and up to three minor versions older;
    - kube-controller-manager, kube-scheduler and cloud-controller-manager are never newer and at most one minor version older;
    - kubectl is within one minor version either way.
  - etcd:
    - etcdctl works with a live member over the network (snapshot save, member list, member remove);
    - etcdutl works directly on data files (snapshot restore, snapshot status);
    - a snapshot is taken from a live member with etcdctl or by copying the db file of a data directory that no etcd process uses;
    - a restore creates the data directory given with --data-dir. If it is a new directory, the etcd-data hostPath in the etcd static Pod manifest must be changed to it; reusing the old path means deleting it and stopping etcd first;
    - restoring means stopping all API server instances, restoring state in all etcd instances and restarting all API servers, and the docs recommend also restarting kube-scheduler, kube-controller-manager and the kubelet;
    - the snapshot file contains all Kubernetes state, and the docs say to encrypt it;
    - etcd should run with an odd number of members, and without a majority Kubernetes cannot change cluster state.
  - HA:
    - stacked versus external etcd topology: stacked is kubeadm's default, couples an etcd member with each control plane instance, and needs at least three control plane nodes; external etcd needs at least three control plane hosts and three etcd hosts;
    - a load balancer in front of kube-apiserver and --control-plane-endpoint, which must be set at init because kubeadm does not support turning a single control plane cluster created without it into an HA cluster;
    - --upload-certs and the certificate key for joining control plane nodes with kubeadm join --control-plane;
    - kube-controller-manager and kube-scheduler run active on one instance at a time through Lease-based leader election, while every kube-apiserver behind the load balancer serves.
  - etcd trap: kubeadm v1.35 deploys etcd 3.6, and etcd v3.6.0 removed etcdctl snapshot restore and etcdctl snapshot status. The v1.35 etcd page still shows them under a "Use etcdctl (Deprecated)" tab, saying they are "slated for removal from etcd v3.6", and much CKA material still uses "ETCDCTL_API=3 etcdctl snapshot restore". No card presents etcdctl as the tool that restores a snapshot, and no card says etcdutl takes snapshots of a live member.
- Scope of 4.4 Installing cluster components, extension interfaces, CRDs and operators (about three cards on Helm and Kustomize, four on interfaces and three on CRDs and operators).
  - Helm and Kustomize as an administrator uses them to install add-ons (a CNI plugin, an Ingress or Gateway controller, metrics-server, an operator):
    - Helm installs the CRDs in a chart's crds/ directory but has no support for upgrading or deleting CRDs;
    - the CRDs must exist before custom resources of those kinds are applied;
    - Kustomize renders overlays of upstream manifests through kubectl kustomize and kubectl apply -k.
    CKAD owns Helm release, revision, values precedence and search behaviour, and the Kustomize fields.
  - Interfaces:
    - the container runtime loads CNI plugins, not the kubelet: the kubelet's network-plugin and cni-bin-dir parameters were removed in v1.24;
    - the project recommends plugins compatible with the CNI v1.0.0 specification (v0.4.0 or later is required);
    - the kubelet talks to the runtime over the CRI, and since v1.26 only CRI API v1 is supported; a runtime without v1 support means the kubelet does not register the node;
    - crictl is a CRI client for nodes;
    - a CSI driver is deployed as a controller part plus a per-node part (usually a DaemonSet), with sidecars such as the external provisioner, resizer and snapshotter, and a CSIDriver object.
  - CRDs and operators:
    - CRD versions, with exactly one version marked as the storage version, served versus storage versions, and conversion;
    - the Established condition, which shows when a new CRD is ready to use;
    - installing an operator as CRDs plus a controller Deployment with RBAC;
    - the operator pattern as defined on kubernetes.io.
    CKAD owns CRD scope, deleting a CRD deleting its objects, schema validation and CEL rules, and CRDs versus API aggregation; KCNA owns what CNI, CSI, CRI and operators are.
  - Helm version trap: Helm 4 is current (v4.3.0). Helm 3 had its final feature release, v3.22.0, in September 2026, with security fixes until February 10, 2027 (helm.sh/blog/helm-v3-end-of-life/). Helm cards test behaviour that holds in both majors ("appliesTo": "Helm 3 and 4").
  - Kustomize deprecations (commonLabels, patchesStrategicMerge, bases) are traps: no card presents them as current.
- Scope of 5.1 Connectivity between Pods, and NetworkPolicy enforcement:
  - The cluster networking model as an administrator configures it:
    - every Pod gets a unique cluster-wide IP;
    - Pods reach Pods on any node directly, without proxies or NAT;
    - agents on a node such as the kubelet reach all Pods on that node;
    - a network plugin implements the model;
    - containers in one Pod share the Pod's network namespace and reach each other over localhost;
    - hostNetwork Pods use the node's network namespace;
    - Pod CIDRs per node, and IPv4/IPv6 dual-stack at concept level.
  - NetworkPolicy from the administrator side:
    - it is enforced only by a network plugin that supports it;
    - policies are namespaced and select Pods only in their own namespace;
    - the control plane sets the immutable kubernetes.io/metadata.name label on every namespace, so a namespaceSelector can target a namespace by name;
    - the "what you can't do with network policies" list (no logging of blocked traffic, no targeting Services by name, no single default policy for all namespaces, nothing TLS-related).
    NetworkPolicy behaviour for hostNetwork Pods and for protocols such as ICMP is undefined in the docs: no cards on either.
  - Ownership: CKAD owns the policy semantics (non-isolated by default, additive allow rules, both ends must allow, empty podSelector, policyTypes defaults, AND versus OR selectors, endPort, DNS under default-deny egress); KCNA owns the basic network model statement and the need for an enforcing plugin.
  - AdminNetworkPolicy and plugin-specific CRDs are out.
- Scope of 5.2 Service types, endpoints and CoreDNS (the control plane and node side).
  - Services:
    - the Service IP range set with kube-apiserver --service-cluster-ip-range;
    - ServiceCIDR and IPAddress objects for allocation tracking and for adding ranges (stable since v1.33);
    - kube-proxy proxy modes on Linux: iptables, ipvs (deprecated since v1.35, with nftables as the recommended replacement), and nftables (stable since v1.33, needs kernel 5.13 or later). Write no card on which mode is the default, and none on the planned ipvs disabling and removal versions that the current docs announce;
    - externalTrafficPolicy Local sends traffic only to node-local ready endpoints, does not forward on nodes without local endpoints, and preserves the client source IP (source-ip tutorial);
    - internalTrafficPolicy Local drops traffic when no node-local endpoint exists;
    - NodePort allocation from --service-node-port-range;
    - a LoadBalancer Service starts as the equivalent of a NodePort Service by default, and a cloud controller manager (or another implementation) provisions the load balancer asynchronously and publishes it in .status.loadBalancer;
    - .spec.loadBalancerIP is deprecated since v1.24;
    - the control plane manages EndpointSlices, and the Endpoints API is deprecated since v1.33.
  - CoreDNS:
    - kubeadm v1.35 supports only CoreDNS (kube-dns support was removed from kubeadm in v1.21);
    - kubeadm runs CoreDNS in kube-system behind a Service still named kube-dns for compatibility, with the label k8s-app=kube-dns;
    - its Corefile lives in the coredns ConfigMap, with the errors, health, ready, kubernetes, prometheus, forward to /etc/resolv.conf, cache, loop, reload and loadbalance plugins;
    - stub domains and upstream servers are configured in the Corefile;
    - the kubelet writes the cluster DNS server and search list into each Pod's resolv.conf;
    - dnsPolicy ClusterFirst is the default; "Default" inherits the node's resolution and is not the default; hostNetwork Pods need ClusterFirstWithHostNet (otherwise they fall back to Default); None requires dnsConfig.
  - The Service .spec.externalIPs field is deprecated only since v1.36, and kube-dns only in v1.37: no cards on either.
  - Ownership: CKAD owns port versus targetPort versus nodePort, selectors and empty EndpointSlices, headless Services and Service DNS names; KCNA owns the definitions of the Service types and of CoreDNS as the default DNS add-on. Diagnosing DNS failures belongs to 2.5.
- Scope of 5.3 Gateway API and Ingress (about seven cards on Gateway API and three on Ingress).
  - Gateway API:
    - an add-on whose kinds are CRDs in the gateway.networking.k8s.io group, installed separately (Standard and Experimental channels) together with a controller, which often installs the CRDs itself;
    - the role-oriented model (Infrastructure Provider, Cluster Operator, Application Developer);
    - GatewayClass is cluster-scoped, each GatewayClass is handled by a single controller named in controllerName, and a functional Gateway needs at least one GatewayClass;
    - a Gateway is associated with exactly one GatewayClass and defines listeners;
    - Routes attach through parentRefs, by default to all listeners of the Gateway; a listener's allowedRoutes.namespaces decides which namespaces may attach (Same is the default), so attachment needs consent on both sides;
    - a ReferenceGrant in the target namespace is required for cross-namespace references, such as an HTTPRoute backendRef to a Service or a Gateway certificateRef to a Secret;
    - HTTPRoute matches, filters and weighted backendRefs (weights are proportional, default 1);
    - TLS termination on a Gateway listener with certificateRefs;
    - the v1.35 kubernetes.io page lists four stable kinds (GatewayClass, Gateway, HTTPRoute, GRPCRoute).
  - Channel trap: the getting-started page still lists TCPRoute, TLSRoute and UDPRoute as experimental, while the type pages say TLSRoute and ListenerSet are in the Standard channel since v1.5.0 and TCPRoute since v1.6.0. Write no card on which channel any route type other than HTTPRoute and GRPCRoute belongs to, none on ListenerSet, BackendTLSPolicy or BackendTrafficPolicy, and none on the API version of any Gateway API kind.
  - Ingress:

    - an Ingress resource does nothing without an Ingress controller, which an administrator deploys (for example with Helm) and exposes through a Service; kube-controller-manager does not start one;
    - several controllers can coexist and are chosen through ingressClassName;
    - ingress2gateway (1.0 announced on 2026-03-20) converts Ingress resources to Gateway API.
  - The Ingress NGINX controller (kubernetes/ingress-nginx) was retired in March 2026, with no further releases, bugfixes or security fixes. Never present it as a current option, and never confuse it with the Ingress API.
  - Ownership: CKAD owns pathType, host and path rules, defaultBackend, TLS from a Secret, and IngressClass with its default annotation; KCNA owns the Ingress versus Gateway API comparison. Controller-specific annotations are out.
