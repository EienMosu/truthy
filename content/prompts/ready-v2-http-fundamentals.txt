DECK
HTTP for web developers: semantics, caching, cookies, connections and the Fetch layer, as the IETF RFCs and the WHATWG Fetch Standard define them.
Taxonomy: frontend > Web platform > topics > HTTP. There is no exam guide. The sources of truth are the RFCs published by the RFC Editor (RFC 9110 HTTP Semantics, RFC 9111 HTTP Caching, RFC 9112 HTTP/1.1, RFC 9113 HTTP/2, RFC 9114 HTTP/3 with RFC 9000 for QUIC, RFC 6265 for cookies, RFC 7838 for Alt-Svc, and the extension RFCs that the sections name) together with their verified errata, the Fetch Standard (fetch.spec.whatwg.org) for browser behaviour, CORS and the fetch() API, and MDN Web Docs for how browsers apply these specifications. The audience is working web developers who read and write HTTP traffic, not implementers of HTTP stacks. Server frameworks, the Node.js http module, CDN products, proxy configuration and wire-level byte layouts are out of scope.

RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.

- Depth: a web developer who debugs HTTP in browser devtools and writes APIs and fetch() calls. Requirement keywords: a card may say a sender "must" or "must not" only where the RFC uses MUST or MUST NOT; where the RFC says SHOULD, MAY or "ought to", the card says "should" or "may", or describes what the RFC allows. Examples verified on 2026-10-08: a message with both Transfer-Encoding and Content-Length "ought to be handled as an error" (RFC 9112), the most restrictive of conflicting directives "should be honored" (RFC 9111), a 416 "SHOULD" carry Content-Range, other recipients "SHOULD ignore" unrecognized fields while proxies "MUST forward" them.
- Version pinning: the pinned specifications are RFC 9110, 9111 and 9112 (June 2022, Internet Standards; RFC 9112 updated only by RFC 9931, March 2026, which no card tests), RFC 9113 and 9114 (June 2022), RFC 6265 (April 2011, still the published cookie RFC on 2026-10-08), RFC 7838, RFC 10008 (June 2026) and the Fetch Standard as last updated on 6 October 2026. Never cite or teach the obsoleted RFC 2616, RFC 7230 to 7235, RFC 7538 or RFC 7540, and never use their terms in a statement: write "content" (not "payload"), "target URI" (not "effective request URI"), "heuristically cacheable" (not "cacheable by default"), 413 "Content Too Large" (not "Payload Too Large"), 416 "Range Not Satisfiable", 422 "Unprocessable Content" (now defined in RFC 9110; MDN's status list still tags it "(WebDAV)", so a 422 card cites RFC 9110). Renames are not knowledge: no "formerly called" cards, and never make a statement false by using an old name. Write no card whose point is an RFC number, a publication year or an RFC's status category; set "appliesTo" to the RFC or standard the card rests on.
- QUERY (RFC 10008, June 2026) is new and older material says no standard method is both safe and able to carry request content. Never write that GET, HEAD or POST are the only choices for a query, that no safe method has defined request content, or that a request with content is never safe or cacheable. QUERY facts that may be tested (at most two cards, in r2, plus at most one in r4): it is safe and idempotent, carries the query in the request content, is cacheable with the request content as part of the cache key, is advertised with Accept-Query, needs a CORS preflight because it is not a CORS-safelisted method, and keeps its method on 301 and 302 (RFC 10008 says the POST-to-GET exceptions do not apply to it, while 303 leads to a GET). MDN's QUERY page says browsers have no specific integration support for QUERY (forms do not send it; fetch() can): any card about browser use of QUERY gets "volatility": "may_change". MDN's QUERY page shows "Unknown specification" in its specification table: QUERY cards cite RFC 10008.
- Request content on GET, HEAD and DELETE: RFC 9110 does not forbid it but gives it no defined semantics and says it might lead some implementations to reject the request; the Fetch Standard makes fetch() and the Request constructor throw a TypeError for a body with GET or HEAD. Each card names the layer it means; never write that HTTP forbids a GET body, and never write that fetch() allows one.
- Safe is not "no side effects": RFC 9110 defines safe as the client not requesting a state change and allows logging and other side effects. PATCH is neither safe nor idempotent by definition (RFC 5789), although a PATCH request can be issued in an idempotent way: no card may say PATCH is idempotent or that it can never be. Proxies must not retry non-idempotent requests automatically; clients should not, unless they know the request semantics are idempotent.
- Status code traps: a client must treat an unrecognized code as the x00 code of its class; 401 must carry WWW-Authenticate, 405 must carry Allow, 407 must carry Proxy-Authenticate; 404 does not say whether the absence is permanent and 410 does; 204 and 304 carry no content and a server must not generate content in a 205; Retry-After is optional (MAY) on 503 and 429. RFC 9110 lists 418 as "(Unused)" while MDN calls it "I'm a teapot", and MDN's status list says 102 Processing was removed from WebDAV (its own MDN page now redirects to the list): write no card on 418 or 102. RFC 8297 (103 Early Hints) was published as Experimental and is now a Proposed Standard through a status change, so no card may call it experimental or turn on its status. MDN's 103 page says most browsers limit support to HTTP/2 or later and only process the first 103 response: at most one 103 card, with "volatility": "may_change"; web-performance owns its effect on TTFB and on preload.
- Redirect traps: RFC 9110 allows, but does not require, a user agent to change POST to GET on 301 and 302, while the Fetch Standard does change POST to GET on 301 and 302 and any method other than GET or HEAD to GET on 303; say which one a card means. The RFC 9110 text for 308 omits the method rule, and verified erratum 7109 adds that a user agent must not change the method, as for 307: cite the erratum (https://www.rfc-editor.org/errata/eid7109) or MDN for 308. 305 Use Proxy is deprecated and 306 is reserved: no card presents them as usable. Write no card on a maximum number of redirects (RFC 9110 only notes an old recommendation of five; the Fetch Standard's limit is a number).
- Negotiation trap: the last row of Table 5 in RFC 9110 Section 12.5.1 is wrong; verified erratum 7138 (not 7306, which is about whitespace in the Range syntax) corrects text/html;level=3 to a quality value of 0.3. Write no card built on that table's last row unless it cites the erratum (https://www.rfc-editor.org/errata/eid7138). Accept-Charset is deprecated (RFC 9110 note: most general-purpose user agents do not send it); the MDN Accept-Charset reference page no longer exists, so such a card cites RFC 9110 and never presents Accept-Charset as something browsers send. Compression, Accept-Encoding for responses, Content-Encoding and Vary: Accept-Encoding belong to web-performance; here Accept-Encoding appears only in a 415 response and as a field a server can send to guide request content.
- Field combination: RFC 9110 says a recipient may combine repeated field lines in order, "separated by a comma" and optional whitespace; a reported (not verified) erratum, 9162, questions whether the separator is a comma or a comma and space. Write no RFC 9110 card whose answer depends on the space; the Fetch Standard's Headers get() joining values with ", " is a separate r14 fact.
- Caching overlap is the main boundary of this deck. web-performance (CWV) already tests, at the level of everyday use: private versus shared caches, max-age counted from response generation and the Age header, s-maxage, max-age taking precedence over Expires, heuristic freshness when no Cache-Control is sent, no-cache versus no-store versus must-revalidate, immutable and its browser support, stale-while-revalidate, revalidation with ETag and If-None-Match or Last-Modified and If-Modified-Since and the 304 response, If-None-Match taking precedence over If-Modified-Since, cache busting and Vary as a cache key. Do not retest those facts. Cards in r6, r7 and r8 test the RFC 9111 and RFC 9110 rules beyond them: which status codes are heuristically cacheable, when a shared cache may reuse a response to a request with Authorization, the storage conditions, Vary matching edge cases, invalidation after unsafe methods, updating stored responses, the request directives, must-revalidate on a disconnected cache, proxy-revalidate, public, qualified private and no-cache, must-understand, Pragma and Warning, stale-if-error and the RFC 8246 limits of immutable.
- Caching traps from RFC 9111: Warning is obsoleted and Pragma is deprecated (MDN marks both pages "Deprecated"), and "Pragma: no-cache" in a response is not a reliable replacement for Cache-Control: no-cache: no card presents Warning or Pragma as current, and a Warning card says "obsoleted" as RFC 9111 does. must-understand is new in RFC 9111. Request directives are advisory ("caches MAY implement them"), so a card says a cache "may honor" them, never that every cache does. The qualified forms of private and no-cache are, per RFC 9111, often handled as the unqualified forms: say so or leave the qualified forms out. Invalidating the Location and Content-Location URIs after an unsafe request is no longer required, only allowed, and never for another origin. The MDN Vary reference page says Vary: * "Implies that the response is uncacheable", while RFC 9111 says a stored response with Vary: * always fails to match: word such a card as RFC 9111 does. Heuristic freshness: RFC 9111 suggests "no more than some fraction" of the time since Last-Modified, with 10% as a typical setting (MDN's Caching guide says the specification "recommends about 10%"); a card may say "typically 10%" only with that qualifier. RFC 8246 says clients should ignore immutable for resources outside an authenticated context such as HTTPS: this is about the connection, not about requests with Authorization, so no card may tie immutable to authenticated requests. A reported RFC 9111 erratum (9004) concerns proxy-revalidate and requests with Authorization: write no card on whether proxy-revalidate lets a shared cache reuse a response to a request with Authorization.
- Cookies: RFC 6265 is the published RFC; its revision (draft-ietf-httpbis-rfc6265bis) was still an Internet-Draft in the RFC Editor queue on 2026-10-08. Write no card about the status of the cookie specifications, never cite the draft, and never present a draft-only feature as standard. RFC 6265's verified erratum 6093 changes "fold" to "combine" in the rule against merging Set-Cookie fields: a card on it says servers should not combine several Set-Cookie fields into one and never uses "fold", which in HTTP means obsolete line folding. The MDN Set-Cookie page gives /docs/Web/HTTP/ (with a trailing slash) as the default path for a cookie set by /docs/Web/HTTP/index.html, while the RFC 6265 default-path algorithm yields /docs/Web/HTTP: default-path cards cite RFC 6265 and do not depend on the trailing slash. RFC 6265 says many user agents are configured to reject public suffixes as a Domain: no card says every user agent does. web-security (WEB) owns Secure, HttpOnly, the security role of Domain and Path, Expires versus Max-Age precedence, SameSite Strict, Lax and None, the missing-SameSite default, the __Secure- and __Host- prefixes, Partitioned cookies and third-party cookies: write no card on them here, except at most one SameSite card on a fact WEB does not test, citing MDN or the Fetch Standard. Cards in r9 test the HTTP mechanism: the two fields, their syntax rules, cookie identity and replacement, the host-only flag, domain-matching, default-path, isolation by host rather than port or scheme, deletion, eviction and the browser's handling of Cookie and Set-Cookie in fetch().
- HTTP/1.x traps from MDN: the Connection management in HTTP/1.x page (September 11, 2026) says HTTP/1.0 connections become persistent when Connection is set to anything other than close, "usually retry-after", which is wrong (the HTTP/1.0 opt-in is the keep-alive connection option, RFC 9112 Section 9.3 and Appendix C.2.2), and it still lists HTTP/2 in cleartext among Upgrade targets although RFC 9113 deprecates the h2c Upgrade: cite RFC 9112 for keep-alive and RFC 9113 for h2c, and cite that MDN page only for pipelining not being activated by default in modern browsers ("may_change") and for domain sharding being deprecated.
- HTTP/2 traps: RFC 9113 deprecates the h2c Upgrade mechanism (cleartext HTTP/2 now starts with prior knowledge) and the RFC 7540 priority scheme (it encourages an alternative such as RFC 9218's); no card presents either as current. RFC 9113 does not state in words that HTTP/2 has no reason phrase (RFC 7540 did); it defines only :status, and MDN's Response.statusText page says HTTP/2 does not support status messages: cite MDN or describe :status. Server push remains defined in RFC 9113 (and HTTP/3 also defines it in RFC 9114), but MDN's HTTP/2 glossary says it has been removed from most major browser engines and replaced by rel="preload" and 103 Early Hints: never write that push was removed from the HTTP/2 or HTTP/3 specification, never write that browsers support it, and give any push card "volatility": "may_change". RFC 9113 says HTTP/2 connections are persistent and clients should not open more than one per host and port; HTTP/2 still suffers head-of-line blocking at the TCP level when a packet is lost (RFC 9114 Section 1.1). HTTP/2 and HTTP/3 do not support 101 Switching Protocols (RFC 9113 Section 8.6, RFC 9114 Section 4.5).
- HTTP/3 traps: MDN's HTTP/3 glossary (October 20, 2025) says QUIC "eliminates the head-of-line blocking problem in HTTP"; RFC 9114 says only that a stream that is blocked or suffers packet loss does not prevent progress on other streams, and still discusses head-of-line blocking that QPACK can cause. Write cards in RFC 9114's terms and never claim that HTTP/3 removes every form of head-of-line blocking. QUIC version 1 uses TLS 1.3 or later. TLS 1.3 is now specified in RFC 9846 (July 2026), which obsoletes RFC 8446: cards say "TLS 1.3" and never cite an RFC number for TLS. HTTP/3 cannot be used for direct access to an http URI (RFC 9114 Section 3.1.2).
- Alt-Svc traps (RFC 7838): the alternative service must present a certificate for the origin's host name, not for the alternative's; the scheme, host and port of the origin and the Host field stay the same; an advertised alternative is fresh for 24 hours from generation of the message unless ma says otherwise, and existing connections to it may continue after that; persist=1 only keeps the entry across network changes; clear invalidates all alternatives of the origin. The 24-hour default may be tested once.
- CORS overlap: web-security (WEB) owns CORS as a browser mechanism: Access-Control-Allow-Origin and the other response headers at a basic level, which methods, headers and Content-Type values trigger a preflight, the rule that Access-Control-Allow-Origin cannot be * with credentials, Access-Control-Expose-Headers, and what JavaScript learns when a CORS check fails. Do not retest those facts (no card in r13 or r14 on a failed CORS check). Cards in r13 test Fetch Standard details beyond them: request modes and the opaque response, when the Origin header is sent, the strict parsing of the safelisted Content-Type and Range values (not the plain fact that a JSON Content-Type needs a preflight), ReadableStream bodies, what a preflight carries and lacks, the ok-status requirement, the irrelevance of Allow, Access-Control-Max-Age and the preflight cache, Authorization and the * of Access-Control-Allow-Headers, the * of Access-Control-Allow-Methods without credentials, the case-sensitive true, and serialized origins. "Simple request" is a term of the obsolete CORS specification; MDN's CORS guide still uses it while saying the Fetch Standard does not: no statement uses it.
- Fetch traps: the request concept in the Fetch Standard defaults to mode "no-cors", while the Request constructor and fetch() given a URL string use "cors": every mode card says fetch() or the Request constructor. fetch() fulfills for any HTTP status, so a 404 or 500 fulfills the promise; it rejects on a network error and also when the input is invalid (TypeError, for example a URL with credentials) or the request is aborted (the signal's reason, an AbortError DOMException by default): never write that a network error is the only cause of rejection. A forbidden method (CONNECT, TRACE, TRACK) makes the Request constructor throw, while a forbidden request-header set through Headers is silently ignored: keep the two outcomes apart. The Fetch Standard uppercases only delete, get, head, options, post and put, so a lowercase "patch" is sent as written. only-if-cached is allowed only with same-origin mode. The Origin header is added to same-origin requests whose method is neither GET nor HEAD, but its value can be null under some referrer policies: word such cards about the header being sent, not about its value. Leave out fetchLater(), service workers, WebSocket and WebTransport modes, the priority option (web-performance), Private Network Access and Local Network Access, the CORS protocol exceptions for report Content-Types, and anything the Fetch Standard calls a legacy construct beyond naming opaqueredirect.
- Numbers: write no card whose answer depends on a number that is a limit or a browser setting: Fetch's redirect limit, the 128-byte and 1024-byte safelist limits, browser caps on Access-Control-Max-Age (MDN lists Firefox and Chromium caps), cookie count and size limits, MDN's parallel connection counts, HTTP/2 window sizes, the 8000-octet URI length recommendation, ports beyond 80 and 443. Fixed specification values that a developer relies on may each be tested once: the 5-second Access-Control-Max-Age default, the 24-hour Alt-Svc default, the status code numbers themselves and the 200 to 299 range of response.ok.
- Browser behaviour: a card about what browsers do (pipelining not activated by default, push removed, 103 handling, QUERY support, preflight redirect support) says "MDN says ..." or names the engines, cites MDN, and gets "volatility": "may_change". RFC behaviour does not change: such cards are "stable".
- Never state a judgement as a fact. A recommendation may be tested only as the source words it, for example "RFC 9110 says a client should not send content in a GET request unless the origin server has indicated support", "RFC 9113 says clients should not open more than one HTTP/2 connection per host and port", "MDN says HTTP redirects execute before JavaScript and HTML redirects", "RFC 9111 says must-revalidate ought to be used only when failing to validate could cause incorrect operation".
