- Scope traps (r5), verified in the execution model, Built-in Functions, the Tutorial, the Programming FAQ and PEP 572: the Tutorial describes the search order as local scope, enclosing functions, module globals, then built-ins; "LEGB" is a community mnemonic the docs do not use, so a statement may state the order but never attribute the acronym to the docs. An assignment anywhere in a function body makes the name local in the whole body; nonlocal naming a variable that no enclosing function scope binds is a SyntaxError at compile time, and nonlocal never refers to a module global; free variables are looked up when the code runs, so lambdas created in a loop all see the loop variable's last value unless a default argument captures it; names bound in a class body are not visible inside its methods, or inside comprehensions and generator expressions in that class body except their leftmost iterable; the iteration variable of a comprehension does not leak into the enclosing scope, also after PEP 709 inlining; a := inside a comprehension binds its target in the containing scope (PEP 572 states this; the 3.14 reference does not, so cite PEP 572, status Final); in a function, each call to locals() returns a fresh dictionary and writing to it does not change the local variables (since 3.13). The default-argument fix for late binding is one fact: test it either in r5 or as the mutable default pitfall in r6, not both.
- Function traps (r6), verified in the compound statements reference and functools: a def statement does not run the function body; default values are evaluated once, left to right, when def runs; *identifier receives a tuple of excess positional arguments and **identifier a new ordered mapping (the Tutorial calls it a dictionary); decorator expressions are evaluated when def runs, and `@f1(arg) @f2 def func` is roughly `func = f1(arg)(f2(func))`, so the decorator nearest the def is applied first; a lambda cannot contain statements or annotations; functools.wraps adds __wrapped__.
- Iterator and generator traps (r7): calling a generator function runs none of its body; an iterator is exhausted after one pass while a list hands out a fresh iterator to each loop; a StopIteration raised inside a generator becomes a RuntimeError (PEP 479); the value of a return statement in a generator becomes StopIteration.value and the value of a yield from expression; a generator expression evaluates its leftmost iterable when it is created, so an error there is raised at once, and everything else lazily; zip and map stop at the shortest input unless strict=True, which raises ValueError. No async generators, no itertools recipes.
- Exception traps (r8), verified in the compound statements reference and the exceptions page: the else clause runs only when control leaves the try suite with no exception and no return, break or continue, and an exception raised in else is not handled by that statement's except clauses; a return, break or continue in finally discards a pending exception, and since 3.14 the compiler emits a SyntaxWarning, not a SyntaxError, for it; the name bound by except ... as is deleted at the end of the clause; KeyboardInterrupt and SystemExit inherit from BaseException, not Exception, so except Exception does not catch them while a bare except does; raise ... from None suppresses the display of the context; ExceptionGroup wraps only Exception subclasses while BaseExceptionGroup wraps any exception, and the BaseExceptionGroup constructor returns an ExceptionGroup when all are Exceptions; a try statement uses except or except*, never both; except* with no type is a SyntaxError, and a matching type that is a subclass of BaseExceptionGroup raises TypeError; break, continue and return cannot appear in an except* clause; a naked exception matched by except* is wrapped in an exception group with an empty message. PEP 758 drops the parentheses only when there is no as clause: `except (A, B) as e` still needs them. The finally SyntaxWarning card belongs to r8 only.
- Context manager traps (r9), verified in the compound statements reference and contextlib: the as target receives what __enter__ returns, which is not always the manager itself; once __enter__ returns without an error, __exit__ is always called; __exit__'s return value is ignored when the block exits without an exception; with A() as a, B() as b behaves like nested with statements, so B exits first; the parenthesized multi-line form exists since 3.10, so it needs no version in the statement; a @contextmanager generator must yield exactly one value; an exception from the block is re-raised at the yield, so cleanup needs try...finally, and a generator that catches it without re-raising suppresses it; managers created with @contextmanager are single-use but can also decorate functions (not generator functions, see the 3.15 rule); ExitStack calls its callbacks in reverse order of registration; contextlib.chdir is not parallel-safe. No async with.
- Class traps (r10, r11), verified in the Tutorial, the data model, Built-in Functions, Built-in Constants and the descriptor HOWTO: x.f() is equivalent to MyClass.f(x); self is a naming convention, not a keyword; name mangling rewrites __spam to _ClassName__spam and nothing in Python enforces data hiding; the MRO uses C3 linearization and super() delegates to the next class in the MRO, which can be a sibling class; zero-argument super() does not work as expected inside nested functions, including generator expressions; implicit special method calls such as len(obj) are only guaranteed to work when the method is defined on the type, so a __len__ stored in the instance dictionary is not used and len() raises TypeError; a class that defines __eq__ without __hash__ gets __hash__ set to None; when a binary method returns NotImplemented Python tries the reflected method, and the right operand's reflected method goes first when its type is a subclass of the left operand's type and provides a different implementation of that reflected method; __getattr__ runs only after normal lookup fails while __getattribute__ runs for every access; data descriptors (with __set__ or __delete__) take precedence over the instance dictionary and non-data descriptors such as functions do not. Dataclass traps: eq is on and order and frozen are off by default; order=True with eq=False raises ValueError; the generated __eq__ compares instances of the identical type only; eq without frozen sets __hash__ to None; an unhashable default such as a list raises ValueError at class creation, and default_factory is the fix; a field without a default after one with a default raises TypeError (keyword-only fields are exempt, so no card may state the rule without that context); dataclasses.replace and copy.replace build the new object through __init__, so __post_init__ runs. No card on dataclass equality between instances whose fields compare equal by identity but not by value, such as NaN (3.13 changed the generated __eq__ to compare field by field).
- Import traps (r12), verified in the import system reference, the import statement reference and the Programming FAQ: a module's code runs once per process and later imports get the cached object from sys.modules; a module whose code raises during import is removed from sys.modules; importlib.reload reruns the code in the same module object; from module import name stores a reference to the object in the local namespace, so a later rebinding of module.name is not visible through that local name; import a.b binds only the top-level name a; importing a submodule binds it as an attribute of the parent package; relative imports work only in the from form; a regular package's __init__.py runs when the package is imported, and namespace packages have no __init__.py. Removed modules (distutils in 3.12, the PEP 594 modules and lib2to3 in 3.13) get at most one card, stated as a removal from the standard library: What's New in 3.12 notes that setuptools still provides distutils, so no card says `import distutils` fails; no card about a planned removal.
- Annotation traps (r13), verified in annotationlib, the compound statements reference, typing and What's New in 3.14: since 3.14, annotations are evaluated lazily, so a forward reference to a name defined later no longer raises NameError when def or class runs, but reading the annotations in the VALUE format (for example through __annotations__) still raises NameError if the name is still undefined; from __future__ import annotations still works and stores annotations as strings, and the reference says it will be deprecated and removed in a future version, but not before Python 3.13 reaches end of life: no card may say it is deprecated, removed or an error today; the docs call annotationlib.get_annotations() the best practice for reading annotations. The runtime does not enforce annotations; @dataclass looks at a field's annotation only to detect ClassVar and InitVar; cast returns its value unchanged; NewType returns its argument at run time; TYPE_CHECKING is False at run time; TypedDict instances are plain dicts; isinstance with a @runtime_checkable protocol checks only that the members exist, not their signatures; Optional[X] means X | None, not an optional parameter; since 3.14 types.UnionType and typing.Union are aliases, so Union[int, str] and int | str create instances of the same runtime type, and no card may say they differ. TypeAlias is deprecated since 3.12 in favour of the type statement, and typing.List, typing.Dict and the other aliases are deprecated since 3.9 but still present: no card says they were removed. Type checkers are third-party: no card about what mypy, Pyright or any checker reports.
- Pattern matching traps (r14), verified in the compound statements reference, the Tutorial and PEP 636: a bare name in a case is a capture pattern that matches anything and binds it, so comparing against a constant needs a dotted name (a value pattern, compared with ==); _ matches anything and never binds; the first matching case wins and there is no fall-through; literal patterns compare with == except None, True and False, which compare with is; f-strings and t-strings cannot be literal patterns; sequence patterns never match str, bytes or bytearray; mapping patterns ignore extra keys; positional subpatterns of a class pattern go through __match_args__, which @dataclass generates; for built-in types such as int and str a single positional subpattern matches the whole subject, so int(0|1) matches 0 but not 0.0; every alternative of an OR pattern must bind the same names; a guard is evaluated only after its pattern matches; a match statement may have at most one irrefutable case block, and it must be last. No card about the bindings a failed pattern may leave behind.
- Never state a judgement as a fact. Python documentation and PEP 8 recommendations may be tested only as "The Python docs recommend ..." or "PEP 8 recommends ..." and only where the page says so (for example annotationlib.get_annotations() as best practice, comparisons to None with is).
