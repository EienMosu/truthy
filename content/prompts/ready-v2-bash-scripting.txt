You are writing content for "Truthy", a mobile true/false card game that teaches IT knowledge. The player sees one statement, answers True or False, then reads a short explanation. A wrong fact in this game teaches people something false, so accuracy matters more than volume.

DECK
GNU Bash scripting for developers and operators.
Taxonomy: devops > Linux > topics > Bash scripting. This is a docs deck, with no exam guide. Pin GNU Bash 5.3 with official patches 001-020, the latest stable release series and patch set listed on 2026-10-08 at https://ftp.gnu.org/pub/gnu/bash/ and https://ftp.gnu.org/pub/gnu/bash/bash-5.3-patches/. Scope comes from the GNU Bash manual, including the upstream Bash 5.3 man page hosted at https://man7.org/linux/man-pages/man1/bash.1.html. Interactive command-line tools and filesystem facts belong to linux-command-line.

SECTIONS (12 cards each, 168 cards in total)
r1 Quoting and word splitting (single, double and ANSI-C quoting, escape characters, concatenated quoted and unquoted word parts, IFS delimiters, explicit and implicit empty arguments, positional-argument forwarding with "$@" and "$*")
r2 Expansion order and word generation (brace expansion; tilde, parameter, command and arithmetic expansion; word splitting; pathname expansion; quote removal; textual brace sequences, assignment contexts, nullglob, failglob, dotglob, globskipdots and GLOBSORT)
r3 Parameter expansion (unset versus null, colon and non-colon forms of -, =, ? and +, length, substring offsets, shortest and longest prefix or suffix removal, pattern replacement, case conversion and indirect expansion)
r4 Arithmetic and command substitution (integer arithmetic, variable evaluation, numeric bases, arithmetic expansion, substitution nesting, stdout capture and trailing newlines in $(...), and Bash 5.3 current-environment forms ${ command; } and ${| command; })
r5 Indexed and associative arrays (declare -a and -A, sparse indices, arithmetic subscripts, negative indexed subscripts, string keys, compound assignment, append, quoted element expansion, element counts and keys, array slicing and unset)
r6 Conditional expressions (if and elif, [[ ]] versus the test and [ builtins, argument boundaries, string, integer, variable and file-test primaries, pattern equality, POSIX extended regular expressions with =~, BASH_REMATCH and short-circuit operators)
r7 Loops and case dispatch (for over expanded words or positional parameters, arithmetic for, while and until, break and continue with nested loops, case pattern selection and the ;;, ;& and ;;& terminators)
r8 Functions and local scope (function arguments and restored positional parameters, $0, return versus exit, last-command function status, local and declare inside functions, dynamic scope, shadowing, recursion and nameref parameters)
r9 Exit status and pipelines (capturing $?, explicit exit statuses, assignment-only command status, &&, || and !, compound-command status, pipeline status with and without pipefail, PIPESTATUS and asynchronous-command status versus wait)
r10 Shell options and error propagation (set -e, -u and -o pipefail, documented errexit exceptions, functions invoked in tested contexts, command substitution and inherit_errexit, arithmetic-command failures, declaration builtins masking substitution failure and nounset-safe parameter forms)
r11 Traps and signal handling (installing, inspecting, resetting and ignoring traps, delayed signal delivery while waiting, EXIT, ERR, DEBUG and RETURN, errtrace and functrace inheritance, cleanup status preservation and limits of catching signals)
r12 Redirections and supplied input (left-to-right descriptor duplication, opening and closing descriptors, exec redirection persistence, grouped redirections, noclobber and >|, quoted and unquoted here-document delimiters, <<- tab stripping and here-string expansion and appended newline)
r13 Subshells, groups and process substitution (( list ) versus { list; }, variable and option persistence, pipeline execution environments, lastpipe with job control disabled, BASHPID versus $$, asynchronous <(...) and >(...), filename arguments, data direction and producer status)
r14 Parsing options and reading data (getopts optstring, OPTARG, OPTIND, explicit argument lists, silent error reporting and parser reuse; read with IFS, -r, -a, -d and -u, REPLY, surplus fields, EOF and a final unterminated line)

STEP 2. Plan the whole deck before writing any card
For every section, list the 12 facts its cards will test, each as a short factKey (kebab-case, for example "ebs-volume-single-az"). The plan must satisfy:
- A factKey appears once in the whole deck. Two cards rest on the same fact if knowing one answer gives you the other, even when one is true and the other false, or when they are worded differently.
- No mirrored pairs (service A wrongly given B's job in one card, and B wrongly given A's job in another). Pick one side.
- No repeated distractor template. If one card is false because "X is described as a firewall", no other card may use that same trick with a different X.
- The facts of a section cover its breadth, not one sub-topic twelve times.
- Half of each section's cards are true and half are false.
Put the plan in the "plan" field of batch b1. In later batches you may deviate from the plan only to fix a problem, and then say so in "notes".

RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: developers and operators who maintain Bash scripts. Test observable argument boundaries, values, status propagation, descriptor destinations, state persistence and control flow. Short inline fragments are appropriate; prefer one relevant expansion or interaction over long output puzzles. Avoid floating-point expectations, platform-specific integer widths, exact diagnostics and timing-dependent outcomes.
- Assumed context: noninteractive GNU Bash 5.3 on Linux, invoked as Bash, with POSIX mode and older compatibility levels disabled. Use LC_ALL=C and default IFS unless specified. Start examples with -e, -u, pipefail, job control, lastpipe, inherit_errexit, errtrace and functrace disabled; leave GLOBIGNORE and GLOBSORT unset. Name any changed option or initial state that determines the answer. These are the deck's controlled example conditions, not claims about distribution defaults.
- Version pinning: use Bash 5.3 with official patches 001-020 throughout. Features introduced in 5.3 must say "In Bash 5.3" in the statement and carry "Bash 5.3" in appliesTo. Older behavior also uses appliesTo "Bash 5.3". Test what the feature does, not its release date. A newer distribution package, development manual or search snippet does not update the pin.
- Verified Bash 5.3 traps: ${ command; } and ${| command; } use the current execution environment, so reserve subshell claims for the specified $(...) form. GLOBSORT makes unconditional name-sorting claims unsafe. array_expand_once replaces the deprecated assoc_expand_once synonym. The 5.3 release NEWS also changes parenthesized multiargument test parsing and says it remains ambiguous. Use current names and omit parsing puzzles involving test's deprecated -a/-o Boolean operators or parenthesized multiargument expressions. Interactive read -E and completion belong outside this deck. Verify these against the release announcement and the matching manual entries.
- Expansion coverage: distinguish the expansion sequence from syntax parsing, and assignment words from ordinary command arguments. Cover the requested expansion families across r1-r4 instead of filling the deck with quotation variants. Keep positional-parameter forwarding in r1 and array-element forwarding in r5. Avoid unspecified locale, directory contents, IFS, glob options or replacement-option settings.
- Conditions, arrays and scope: test patterns separately from regular expressions, and string comparisons separately from arithmetic comparisons. Use supplied file states for file-test expressions; filesystem mechanics remain outside this deck. Array examples must identify indexed or associative type, existing elements and relevant quoting. Avoid associative-key iteration order, multidimensional-array claims and subscript reevaluation edge cases. Function examples should expose dynamic local scope and argument restoration. For namerefs, distinguish a scalar nameref referencing an array from an array variable carrying the nameref attribute.
- Error handling: cover the documented exceptions to -e and ERR, tested function-call contexts, command-substitution inheritance, nounset exceptions and guarded parameter forms. No blanket claim that a "strict mode" catches failures. Reserve arithmetic-command zero-result status and declaration masking such as local value=$(...) for r10. Put the pipeline result selected by pipefail in r9 and its interaction with -e in r10. Verify the complete surrounding syntax before selecting a failure-propagation fact.
- Traps and asynchronous work: specify foreground waiting versus wait, caught versus ignored signals, and the inheritance options in force. Capture status explicitly in cleanup examples; avoid relying on exit without an argument inside nested trap contexts, whose rules changed in 5.3. Process substitution is asynchronous and has separate status handling; avoid fixed completion order or unverified wait claims. Generic signal numbers and kill administration are outside scope.
- Redirection and input coverage: give the initial descriptor destinations when order determines the outcome. Allocate about six r12 cards to descriptors and six to here documents and here strings. Allocate about six r14 cards to getopts and six to read. Keep read's builtin field assignment and EOF behavior in r14; r7 owns loop control, while r13 owns whether a pipeline-fed loop preserves variables.

Do not turn the same mechanism into a second fact in another section.
