DECK
Java fundamentals for working developers: the language and its core APIs as Java SE 25, the current long-term support release, defines them.
Taxonomy: backend > Java > topics > Fundamentals. There is no exam guide; the fourteen sections r1 to r14 are this deck's own split of the topic. The sources of truth are The Java Language Specification, Java SE 25 Edition (docs.oracle.com/javase/specs/jls/se25/html/), the Java SE 25 API documentation and guides on docs.oracle.com (docs.oracle.com/en/java/javase/25/), the JEPs and JDK project pages on openjdk.org for which release finalized or previewed a feature, and the tutorials on dev.java where the Java 25 pages confirm them. The audience is working developers who write Java every day. Preview and incubator features are out of scope, and so are frameworks (Spring, Jakarta EE), build tools (Maven, Gradle), JVM internals (garbage collectors, the JIT, object layout, AOT caching), JDBC, I/O beyond try-with-resources, serialization, reflection and the java.net.http client.

- Renamed features: JEP 512 and the Java 25 guide use the names "compact source file" and "instance main method"; the JLS 25 calls such a file a compact compilation unit (7.3) and its class an implicitly declared class (8.1.8), so those terms are correct too. - Wrapper trap (r1): the JLS guarantees identical boxes only when a constant expression with the value true, false, a char from U+0000 to U+007F, or an integer from -128 to 127 is boxed, and Integer.valueOf "will always cache values in the range -128 to 127, inclusive, and may cache other values outside of this range". So write identity cards with literals or constants (Integer a = 127, b = 127) or explicit Integer.valueOf calls; a card may say that == on those two Integer objects is true, but no card may say that == on boxed values outside that range is false: it is unspecified. The Integer(int) constructor is @Deprecated(since="9") in Java 25, 26 and 27, while the Java 16 to 24 pages say "Deprecated, for removal" and much study material still says so: any card on it says "In Java 25", and no card says the constructors are removed or scheduled for removal. The Integer docs say valueOf "should generally be used in preference to the constructor": test that only as worded.
- String traps (r2): string literals and constant expressions are interned (JLS 3.10.5), runtime concatenation creates a new String unless the expression is a constant expression (JLS 15.18.1), a final local String initialized with a constant expression is a constant variable (JLS 4.12.4); StringBuilder does not override equals (its Javadoc API note); the opening """ of a text block must be followed by a line terminator, and trailing spaces on content lines are stripped unless escaped with \s. No cards on compact strings, string deduplication, String.hashCode caching or where the string pool is stored.
- Equality traps (r3): the hashCode contract does not require unequal objects to have different hash codes; arrays do not override equals; a record's equals compares components, so a record with an array component compares that array by reference (test this in r5 only); the Comparable page names BigDecimal as the core class whose natural ordering is inconsistent with equals (4.0 and 4.00), so a TreeSet treats them as one element while a HashSet keeps both. Value-based classes (the wrappers, Optional, java.time classes; List.of and Stream.toList results "may be value-based"): the ValueBased page says a program should not try to distinguish the identities of equal instances and that synchronization on them is strongly discouraged, and the List, Set, Map and Stream.toList docs call identity-sensitive operations on their results "unreliable"; quote the page that states the fact you test.
- Class and constructor traps (r4, r5): the default constructor has the same access modifier as its class, or package access when the class has none, not always public; fields and static methods are not overridden (fields are hidden and resolved from the static type; static methods are hidden); the overload is chosen at compile time from the static types of the arguments, and the override is chosen at run time; in a flexible constructor body the prologue may not use this, read fields, call instance methods or use super to reach superclass members, may assign fields of the same class that have no initializer, and may not contain a return statement, while a canonical record constructor still may not contain this(...) or super(...); a class does not inherit static methods from its superinterfaces (JLS 8.4.8); a default method that is override-equivalent with a non-private method of Object is a compile-time error (JLS 9.4.1.2); enum constructors may not be public or protected; an enum class is implicitly final, or implicitly sealed when a constant has a class body, so never write "enums are always final"; records cannot declare instance fields or extend a class, but may implement interfaces and declare static fields, static and instance methods and nested types; record fields are final, but the objects they refer to may be mutable.
- Pattern and switch traps (r6): an arrow-label switch never falls through, a colon-label switch does unless break; switch expressions and enhanced switch statements must be exhaustive, while a switch statement that is not enhanced need not be; a switch statement is enhanced only when it has a case pattern or case null label, or a selector type other than char, byte, short, int, their wrappers, String or an enum (JLS 14.11.2), so the arrow form alone does not make it enhanced: an arrow-label switch statement over an enum that omits a constant compiles and does nothing for it, while a switch expression over the same enum must cover every constant or have a default; a switch over a sealed interface whose permitted subtypes are all covered needs no default; a null selector throws NullPointerException unless a case null label applies, even with a default label; a dominated case label is a compile-time error; in a sealed hierarchy every permitted subclass must be final, sealed or non-sealed, and in the unnamed module they must share the sealed class's package. Write no card on MatchException beyond its existence for an enhanced switch that no label matches at run time (for example after separate compilation).
- Generics traps (r7): List<Integer> is not a subtype of List<Number> while Integer[] is a subtype of Number[], and storing a Double through that Number[] reference throws ArrayStoreException; you can add Integer values to a List<? super Integer> and read them only as Object, and you can add nothing but null to a List<? extends Number>; generic type information is erased, so two methods that differ only in List<String> versus List<Integer> parameters clash. "PECS" is a mnemonic from third-party books, not from the official sources: no card attributes it to them. Write no card about instanceof with a parameterized type (its rules changed with pattern matching) and none on reifiable-type edge cases beyond new T[] and generic array creation.
- Collection traps (r8): HashMap and HashSet give no ordering guarantee, and their pages say the order may not remain constant over time; Set.of and Map.of iteration order is unspecified and subject to change, so no card says they keep argument order (List.of does); List.of, Set.of and Map.of reject nulls with NullPointerException and Set.of and Map.of reject duplicates with IllegalArgumentException; the docs call the results of List.of, Set.of, Map.of, copyOf and Stream.toList "unmodifiable", not immutable, because their elements may be mutable: use the docs' word; Collections.unmodifiableList is a read-only view that reflects changes to its backing list; Arrays.asList supports set but not add or remove; reversed() returns a view, not a copy; TreeSet is a SequencedSet, but the SortedSet docs say its addFirst and addLast always throw UnsupportedOperationException, and LinkedHashSet.addFirst relocates an element that is already present; HashMap permits one null key, ConcurrentHashMap permits neither null keys nor null values, and TreeMap.put throws NullPointerException for a null key when the map uses natural ordering; ConcurrentModificationException is thrown on a best-effort basis, so no card says it is guaranteed. No cards on initial capacities, load factors, resize thresholds or treeification.
- Lambda and var traps (r9): the JLS defines a functional interface as an interface that is not declared sealed and has exactly one abstract method, not counting public methods of Object; var is inferred at compile time and the variable stays statically typed; `var x = null;`, `var a = {1, 2};`, `var b = 1, c = 2;` and var with a lambda or method reference initializer are compile-time errors (JLS 14.4 and 14.4.1); var is not allowed for fields, method parameters or return types, but is allowed for lambda parameters; a lambda may read but not reassign a captured local variable, and the variable must be effectively final even if the lambda only reads it; inside a lambda, this refers to the enclosing instance.
- Stream and Optional traps (r10): intermediate operations do nothing until a terminal operation runs, and the Stream docs allow an implementation to elide operations, so peek output is not guaranteed; a stream can be used once, and the docs say an implementation "may" throw IllegalStateException on reuse, so keep "may"; Collectors.toList gives no guarantee on type, mutability, serializability or thread-safety, while Stream.toList (Java 16) is unmodifiable; Collectors.toMap throws IllegalStateException on duplicate keys unless a merge function is given; orElse evaluates its argument even when a value is present, orElseGet calls its supplier only when empty; Optional.of(null) throws NullPointerException. The Optional API note says it is "primarily intended for use as a method return type": test that only as the docs word it. Write no card on parallel stream performance, the common pool size, spliterator characteristics or whether Stream.toList accepts null elements.
- Exception traps (r11): the compiler enforces catch-or-declare only for checked exceptions, and the JVM does not; resources declared in a try-with-resources header are implicitly final, closed in reverse order of initialization and before any catch or finally clause of the same try statement runs, and a null resource is not closed; an exception thrown by close() is suppressed when another exception is already propagating; a return in finally discards an exception from the try block; catching a superclass before its subclass makes the later catch a compile-time error. Write no card on finalization or Object.finalize (deprecated for removal) and none on the Security Manager (permanently disabled since Java 24).
- Concurrency traps (r12, r13): volatile gives visibility and ordering but count++ on a volatile field is still not atomic; calling run() executes the task on the current thread; Thread.sleep inside a synchronized block keeps the monitor ("does not lose ownership of any monitors") while wait releases it; wait and notify outside the monitor throw IllegalMonitorStateException; Future.get wraps the task's exception in ExecutionException; ExecutorService extends AutoCloseable and close() waits for submitted tasks (since Java 19, before the pin's baseline, so no version in the statement). Virtual threads are not faster threads: the Java 25 guide says they "exist to provide scale (higher throughput), not speed (lower latency)" and "should never be pooled". Since Java 24, synchronized blocks and Object.wait no longer pin a virtual thread; much material written for Java 21, including the dev.java virtual threads tutorial on 2026-10-08, says to replace synchronized with ReentrantLock to avoid pinning: never teach that as current, never cite dev.java for pinning, and write no card on the jdk.tracePinnedThreads property, which JEP 491 made unnecessary.
