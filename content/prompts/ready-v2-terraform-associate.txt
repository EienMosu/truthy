RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: a cloud engineer who has run the Terraform CLI and written HCL. Test behaviour: what a command, block, meta-argument, function or backend does, when Terraform reads or writes state, what init, validate, plan, apply and destroy each check or change, how values flow between modules, and which HCP Terraform feature does what. No trivia about file names, exact flag spellings beyond the ones the exam content list names, or exam logistics (price, duration, question count).
- Version pinning: the exam tests Terraform 1.12, while the documentation's latest version is newer (the version switcher shows a newer latest release and a beta). Check every Terraform card against the /v1.12.x/ pages and leave out anything that is new after 1.12 or marked experimental, alpha or beta in them (for example configuration generation with plan -generate-config-out is experimental in 1.12). Features with a minimum version must state "Since Terraform 1.x" or set "appliesTo" accordingly, with the minimum version taken from the official page: the 1.12 pages give the sensitive argument 0.15, input variable validation 0.13, preconditions and postconditions 1.2, check blocks 1.5, the ephemeral argument and ephemeral block 1.10, write-only arguments 1.11, and removing and importing resources through configuration 1.7; for the import, moved and removed blocks on their own, confirm the version on their pages or leave the version out.
- Secrets in state is the classic trap of this exam. The official 004 sample question still says that usernames and passwords referenced in the code, even as variables, end up in plain text in the state file; in Terraform 1.12 that is true of ordinary and sensitive values but not of ephemeral ones. The sensitive argument only redacts values from CLI output and the HCP Terraform UI, and Terraform still stores them in state and plan files; ephemeral values (the ephemeral argument on variables and child module outputs, the ephemeral block, write-only arguments on managed resources) are omitted from state and plan files, and which ephemeral blocks and write-only arguments exist depends on the provider. Every card on this topic in 4.5 or 2.2 names which of the two mechanisms it is about.
- Deprecated commands: terraform refresh is deprecated in favour of the -refresh-only flag on plan and apply, and terraform taint is deprecated in favour of apply -replace. A card may test that replacement, but never present the deprecated command as the recommended way.
- Renamed products: Terraform Cloud has been called HCP Terraform since April 22, 2024; use "HCP Terraform" and never the old name. Terraform Enterprise is the self-hosted distribution of HCP Terraform. The exam page expects candidates to "identify Terraform Enterprise features and distinguish them from Community edition", so a card may test whether a capability needs HCP Terraform or Terraform Enterprise (remote runs, policy enforcement, the private registry, team permissions) or is available with the Terraform CLI alone; do not mix these products up in a statement.
- "Workspace" means two different things: CLI workspaces (terraform workspace, several states for one configuration and backend) and HCP Terraform workspaces (a unit with its own configuration, variables, state and runs). Every card that mentions a workspace says which one.
- HCP Terraform is a hosted service whose documentation is unversioned and changes often. Leave out HCP Terraform edition names and which edition includes what, user limits, pricing, Stacks (not in the 004 content list) and anything marked beta (for example the native Terraform policy framework); policy cards stay with Sentinel and OPA. Set "volatility" to "may_change" for any HCP Terraform card whose answer depends on a feature's packaging or availability.
- Never state a judgement as a fact. "Best practice" or "recommended" is acceptable only when the official page says so (for example keeping state out of version control, or preferring -replace over taint).
- Keep sections apart where the objectives overlap: 2.2 covers why state exists and what it records; 6.1 covers where state is stored and locking; 6.2 covers drift, refresh-only mode and the moved and removed blocks; 7.1 covers import and the CLI commands that inspect state (state list, state show, show) and TF_LOG logging. The dependency lock file belongs to 2.1, what terraform init does to 3.1, the dependency graph to 3.2 unless a card is about depends_on (4.4), and the private registry to 8.2 rather than 5.1.
- Provider-specific knowledge is not part of this exam (the content list says so): never test arguments or behaviour of a particular AWS, Azure or Google Cloud resource type. Example configurations in statements use generic resource names. Vault is tested only as Terraform consumes it (the vault provider, injecting secrets); Vault itself and CI pipelines belong to other decks (github-actions), and cloud services belong to the AWS, Azure and Google Cloud decks.
