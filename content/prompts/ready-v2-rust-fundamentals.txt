No card on Polonius, the next-generation trait solver or two-phase borrows: they are nightly or implementation details.
- Ownership and trait traps, verified in the std docs: shared references are Copy and mutable references are not; a type with a Drop implementation cannot be Copy; Clone is a supertrait of Copy; derive(Clone) clones each field, so cloning a struct holding an Arc<Mutex<T>> shares the state (std Clone docs); Drop::drop cannot be called directly and std::mem::drop takes ownership to drop early; locals drop in reverse order of declaration and struct fields in declaration order; f32 and f64 implement PartialEq and PartialOrd but neither Eq nor Ord; derived PartialOrd orders struct fields lexicographically from top to bottom and enum variants primarily by discriminant, which by default is smallest for the first variant; equal keys must hash equally, and breaking that is a logic error, not undefined behaviour; the From docs say to prefer implementing From, which gives Into through a blanket implementation, and also say to prefer Into over From in the trait bounds of a generic function, so no card says Into should never be used. Use today's names: "dyn compatible" and "dyn compatibility" (the Reference notes the concept "was formerly known as object safety"): never write "object safe" in a statement. Per the Reference's dispatchability rules, a method with type parameters, a method that uses Self outside the receiver (such as returning Self), an async fn or a return-position impl Trait method makes a trait unusable as dyn unless that method has a where Self: Sized bound, and a trait with an associated constant or with Sized as a supertrait is not dyn compatible; test only these rules as the Reference states them, and never write that a trait with an async fn cannot exist.
- Orphan rule (r8), verified in the Reference: an implementation is allowed when the trait or at least one of the types in it is defined in the current crate, with rules about uncovered type parameters, and Box<LocalType> counts as local; cards use the Book's level ("implement a trait on a type only if the trait or the type is local to your crate") and the newtype pattern, with no card on uncovered type parameters or fundamental types.
- Enum cast trap (r5), verified in the Rust 1.86.0 compatibility notes: casting a field-less enum to an integer with as is an error when the enum implements Drop, so a cast card uses an enum without a Drop implementation and no card says every field-less enum can be cast.
- Error and panic traps (r7), verified in the Book, the Reference and the std docs: ? on Err returns Err(From::from(e)), so a ? in a function returning Result<_, Box<dyn Error>> converts many error types; ? works on Option in a function returning Option, but ? does not turn an Option into a Result (ok_or does); main may return Result<(), Box<dyn Error>> as the Book shows, the process exits with 0 for Ok(()) and a nonzero value for Err, and the Book says main may return any type that implements std::process::Termination (the std docs implement it for Result<T, E> where E: Debug): test main return types only at that level; panicking unwinds and runs destructors by default, while panic = 'abort' in a profile ends the process without unwinding; std::process::exit runs no destructors on any thread's stack; integer overflow panics in the dev profile (overflow-checks = true) and wraps in two's complement in a default release build (overflow-checks = false), so every overflow card names the build ("in a debug build", "in a default release build") and none says overflow is undefined behaviour or always wraps; the Book adds that relying on wrapping is considered an error. The Book's advice on when to panic may be tested only as "The Rust Book recommends ...".
- Smart pointer and concurrency traps (r11, r12), verified in the Book and the std docs: Rc<T> is for single-threaded code and is neither Send nor Sync; Rc::clone increments the reference count and does not deep-copy; Rc<T> gives only shared access, so mutation needs interior mutability; RefCell checks borrows at run time and borrow_mut panics while another borrow is active, while try_borrow_mut returns a Result; Cell, RefCell and OnceCell are not Sync (the std docs name RwLock, OnceLock and LazyLock as their Sync counterparts); reference cycles of Rc leak memory and the Book calls memory leaks memory safe; Weak::upgrade returns an Option; thread::spawn needs a Send + 'static closure, so borrowing local data needs a move closure or thread::scope; spawned threads are shut down when the main thread completes, whether or not they have finished; JoinHandle::join returns Err when the thread panicked; mpsc means multiple producer, single consumer, Sender can be cloned and Receiver cannot; channel() is infinitely buffered and its send never blocks for space, while sync_channel(0) is a rendezvous channel; recv returns Err once every Sender is dropped; a Mutex is poisoned when a thread panics while holding the guard and poisoning is advisory (PoisonError::into_inner returns the guard); the compiler prevents data races but not deadlocks; T is Sync exactly when &T is Send; implementing Send or Sync by hand requires unsafe. std::sync::mpmc, std::sync::nonpoison, std::sync::oneshot and std::sync::poison are experimental: no card says Rust has a stable multi-consumer channel or a non-poisoning Mutex, and no card says it lacks one.
- Iterator and closure traps (r10), verified in the Book, the Reference and the std docs: adapters such as map do nothing until a consuming method runs, and the compiler warns that iterators are lazy; iter() yields &T, iter_mut() &mut T and into_iter() on a Vec yields T; collect needs a target type from an annotation or turbofish; the closure traits are inferred from what the body does with captured values, not from the move keyword (a move closure can still implement Fn); the std Fn docs say FnMut and FnOnce are supertraits of Fn; non-capturing closures coerce to fn pointers. Rust 1.94 changed fine details of closure capture around patterns, and Rust 1.95 made matching on a #[non_exhaustive] enum read the discriminant inside closures: write no card on partial captures through match or destructuring inside a closure, only the Book-level capture modes and the 2021 disjoint field capture. Rust 1.99 added IntoIterator for Box<[T; N]>: write no card about iterating a boxed array.
- Unsafe traps (r14), verified in the Book and the Reference: the Book lists five unsafe superpowers, but the Reference's list of unsafe operations is longer (declaring an extern block, applying an unsafe attribute, calling a target_feature function from code without those features), so no card says unsafe Rust adds exactly five abilities; a card may say "The Rust Book lists ... as an unsafe superpower". Creating a raw pointer is safe and dereferencing it is not; unsafe does not turn off the borrow checker; in the 2024 edition the body of an unsafe fn needs unsafe blocks for unsafe operations (a warning, not an error), extern blocks must be written unsafe extern, references to a static mut are denied by default (a deny-by-default lint), and std::env::set_var and remove_var are unsafe functions. Leave out FFI details, C-variadic functions (Rust 1.99), naked functions, inline assembly, unions beyond naming them, MaybeUninit, pointer provenance, Miri, transmute and the Box::leak guidance of Rust 1.99.
- Async traps (r14), verified in the Book and the Reference: an async fn does no work when called and returns a future that runs its body when polled; the Book says futures are lazy and do nothing until awaited, unlike a spawned thread, which starts running immediately; the Reference says .await is legal only in an async fn, an async block or an async closure (the Book mentions only async functions and blocks: cite the Reference for closures); the standard library ships no executor and main cannot be marked async, so async code needs a runtime from a crate; Future::poll returns Poll::Pending or Poll::Ready and takes Pin<&mut Self>; the Reference says the AsyncFn, AsyncFnMut and AsyncFnOnce traits are not dyn-compatible. Write no card about the API of tokio, futures, trpl or any runtime (including #[tokio::main] and block_on), about Stream or async iterators (std::async_iter is nightly-only), about Waker internals or the Pin and Unpin rules beyond "poll takes Pin<&mut Self>", or about async fn in dyn traits beyond the Reference's rule.
- Cargo traps (r13), verified in the Cargo Book: a manifest without an edition key is built as 2015, and cargo new writes edition = "2024"; a dependency written "1.2.3" is a caret requirement (>=1.2.3, <2.0.0) and "0.2.3" means >=0.2.3, <0.3.0; the Cargo FAQ no longer says libraries should not commit Cargo.lock: cargo new tracks it by default and the choice depends on the package's needs (no card repeats the old library rule); features should be additive because Cargo unifies them; edition = "2024" implies resolver = "3", the Rust-version aware resolver, but the resolver is a workspace-wide setting honored only at the top-level package, and a virtual workspace must set it explicitly; the dev profile has overflow-checks = true and the release profile overflow-checks = false, and both default to panic = 'unwind'.
