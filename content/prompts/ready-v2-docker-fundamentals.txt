You are writing content for "Truthy", a mobile true/false card game that teaches IT knowledge. The player sees one statement, answers True or False, then reads a short explanation. A wrong fact in this game teaches people something false, so accuracy matters more than volume.

DECK
Docker fundamentals for developers: images, containers, Dockerfile and builds, cache, storage, networking, Compose, registries and security basics.
Taxonomy: devops > Docker > topics > Fundamentals. There is no exam guide that tracks the current product (the Docker Certified Associate exam is still offered, but by Mirantis, and it also covers orchestration and Mirantis products); the official documentation on docs.docker.com is the source of truth. The audience is working developers who build and run containers.

SECTIONS (12 cards each, 144 cards in total)
r1 Containers, images and the Docker Engine architecture (image versus container, containers versus virtual machines, namespaces and control groups, the Docker client, dockerd and its REST API, Docker objects, Docker Desktop versus Docker Engine)
r2 Running and managing containers (docker run options such as -d, --rm, -e, --name and --entrypoint, the lifecycle commands create, start, stop, kill, restart, rm, exec and logs, the stop signal and grace period, restart policies, docker run exit codes 125, 126 and 127, no resource limits unless you set them)
r3 Dockerfile instructions (FROM, RUN, COPY versus ADD, CMD versus ENTRYPOINT, shell form versus exec form, ARG versus ENV, WORKDIR, EXPOSE, HEALTHCHECK, LABEL, STOPSIGNAL, the syntax parser directive, heredocs; USER belongs to r12)
r4 Build context and BuildKit (Buildx as client and BuildKit as builder, docker build as a wrapper around Buildx, build context types including Git URLs, tarballs and stdin, .dockerignore and Dockerfile-specific ignore files, named contexts with --build-context, build drivers, status of the legacy builder, build checks)
r5 Multi-stage and multi-platform builds (FROM ... AS, COPY --from a stage name, index or external image, --target, which stages BuildKit skips versus the legacy builder, what ends up in the final image, manifest lists, --platform, QEMU emulation, cross-compilation with BUILDPLATFORM and TARGETPLATFORM)
r6 Layers and build cache (what a layer contains, the union filesystem and the container's writable layer, layer sharing between images, cache invalidation rules for RUN, COPY, ADD, build arguments and secrets, instruction order, RUN --mount=type=cache and type=bind, external cache with --cache-from and --cache-to, --no-cache and --pull)
r7 Image references, tags, digests and registries (registry versus repository, the [HOST[:PORT]/]NAMESPACE/REPOSITORY[:TAG] format and its defaults docker.io, library and latest, mutable tags versus immutable digests, pinning a base image by digest, docker login, push and pull, the Docker Hub trusted content categories Docker Official Images, Verified Publisher and Docker-Sponsored Open Source, the containerd image store versus classic storage drivers; Docker Hardened Images belong to r12)
r8 Volumes (named versus anonymous volumes, lifecycle and removal including --rm, the default scope of docker volume prune, pre-population from image content and volume-nocopy, read-only mounts, volume drivers, -v versus --mount syntax)
r9 Bind mounts and tmpfs mounts (host path behaviour with -v versus --mount, container content obscured by a mount, write access to the host, bind propagation, SELinux z and Z options, when a bind mount fits better than a volume, tmpfs platform support, lifetime and sharing)
r10 Networking (default bridge versus user-defined bridge networks, the embedded DNS server and name resolution, the drivers bridge, host, none, overlay, macvlan and ipvlan, publishing ports with -p and the default host address, binding to localhost, container-to-container traffic on one network, --network container:<name>, legacy links and their deprecation on the default bridge)
r11 Docker Compose (compose.yaml and the Compose Specification, the obsolete top-level version element, docker compose versus docker-compose and the Compose v2 and v5 CLIs, the project name, the default project network and service-name DNS, CONTAINER_PORT versus HOST_PORT, depends_on and its conditions, profiles, Compose Watch and its actions, merging multiple Compose files)
r12 Security basics (who may control the daemon, rootless mode versus userns-remap, Linux capabilities with --cap-drop, --cap-add and --privileged, seccomp and AppArmor profiles, running as a non-root USER, build secrets and SSH mounts versus ARG and ENV, Docker Scout SBOM and vulnerability analysis, Docker Hardened Images)

RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: a developer who builds and runs containers every day. Test behaviour: what persists and what is lost, what invalidates the build cache, what is reachable from where, what an instruction, flag or Compose attribute does, and which default applies when you set nothing. No trivia about command output formats, rarely used flags or exact error messages.
- Version pinning: pin the current Docker Engine major (29 at the time of writing), Compose v5 and the docker/dockerfile:1 syntax, and recheck them in step 1. Several defaults changed recently and must carry the version inside the statement and in "appliesTo": the containerd image store is the default only for fresh installs of Engine 29.0 and later (upgraded daemons keep the overlay2 graph driver until the containerd image store is enabled); since Engine 29.0 legacy link environment variables are no longer set by default (removal is planned for Engine 30); BuildKit is the default builder for Linux images since Engine 23.0 and the legacy builder is deprecated for Linux images. Cards about behaviour that is the same in every supported version leave the version out of the statement and set "appliesTo" to the pinned current versions.
- Compose naming trap: Compose v1 (Python, docker-compose) is gone; the supported CLIs are Compose v2 and Compose v5, which are functionally identical, v5 adding an official Go SDK and jumping to v5 to avoid confusion with the old file format versions 2.x and 3.x. The top-level version element is obsolete and only informative; Compose validates with the most recent schema regardless of it. Never write a card that treats file format "version 3" as current.
- Other deprecated or renamed things that must not appear as current: MAINTAINER (use LABEL), the legacy "ENV name value" syntax, --link on the default bridge network (deprecated, warning since Engine 29.6), the --time flag of docker stop and docker restart (renamed --timeout), cgroup v1 (deprecated in Engine 29). Docker Content Trust and Notary v1 are being retired (removed from the CLI in Engine 29, notary.docker.io shuts down on 2026-12-08): write no cards about Docker Content Trust or docker trust, and ignore the trust pinning passage that /engine/security/ still contains.
- Known misconceptions worth testing (each at most once in the deck): EXPOSE documents a port but does not publish it; the latest tag is only the default tag, not the newest image; tags are mutable and digests are not; published ports bind to all host addresses unless a host IP is given; depends_on waits for a running container, not a ready one, unless a condition says so; -v creates a missing host directory for a bind mount while --mount errors unless bind-create-src is set; docker volume prune removes only anonymous volumes unless --all is given; the RUN cache is not invalidated automatically and file mtime is ignored by the COPY and ADD checksum; secret values are not part of the build cache; the shell form of ENTRYPOINT ignores CMD and run arguments and does not pass signals; ARG and ENV values persist in the image history or config and are no place for secrets.
- Platform scope: cards are about Docker Engine on Linux with Linux containers unless the statement says otherwise. tmpfs mounts are Linux only and bind propagation does not work with Docker Desktop: say "On Linux" or "With Docker Desktop" in the statement whenever the answer depends on it. Leave out Windows containers (including the fact that Windows image builds still use the legacy builder).
- Build drivers: the feature table on /build/builders/drivers/ marks multi-arch images as unsupported for the docker driver, while /build/building/multi-platform/ says the containerd image store supports multi-platform images out of the box. Write no card whose answer depends on whether the default docker driver can build multi-platform images.
- Leave out Swarm mode beyond identifying the overlay driver, Mirantis and Docker Enterprise products, Docker Desktop licensing and plans, Docker Hub rate limits and plan quotas, Docker Build Cloud and the cloud driver beyond naming it, Kubernetes inside Docker Desktop, image mounts, anything marked experimental (for example the nftables firewall backend), Dockerfile labs syntax, and Compose features the release notes call partial (jobs).
- Leave out numeric defaults (stop grace period, the restart-policy 10 second rule, tmpfs default size, number of default capabilities, concurrent downloads, the embedded DNS address, the Compose version that introduced a watch action); test the behaviour, not the number.
- Never state a judgement as a fact. Docker's own recommendations may be tested only as "Docker's build best practices recommend ..." and only when the best practices page says so.
- Docker Scout and Docker Hardened Images are products whose packaging and tiers change (DHI has Community, Select and Enterprise editions): test what they do, not their plans, and set "volatility" to "may_change" for any card that depends on their names or availability.
- Overlap with other decks: kubernetes-kcna owns orchestration, pods, the CRI and runtimes such as containerd as a Kubernetes component; github-actions owns Docker actions and build-push-action in CI; web-security owns application security (OWASP, XSS, CSRF); aws-dva-c02 and gcp-ace own ECR, ECS, Artifact Registry and Cloud Run. Keep every card about the Docker CLI, Engine, Dockerfile, BuildKit and Compose themselves.
- Inside this deck, keep each concept in one section: HEALTHCHECK as an instruction in r3 and Compose healthcheck conditions in r11; the USER instruction and non-root execution only in r12; build secrets only in r12, cache invalidation by secrets only in r6; EXPOSE only in r3, port publishing only in r10; layers only in r6; Docker Hardened Images only in r12.
