TypeScript: the type system and the compiler options that change it.
Taxonomy: frontend > TypeScript > topics > Fundamentals. RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: a developer who writes TypeScript every day. Test what the checker does: what is assignable to what, what a check narrows a type to, what a type operator, conditional type, mapped type or utility type produces, what a compiler option changes, and what exists only at compile time versus what is emitted as JavaScript. A statement may contain a short inline code fragment in backticks when the whole statement still fits in 120 characters, for example "`keyof { a: 1; b: 2 }` is the type `\"a\" | \"b\"`".
- Version pinning: TypeScript 7.0 is the current version, and its type checking is meant to match TypeScript 6.0. Defaults changed in 6.0 (strict is true, module is esnext, target is the newest supported ECMAScript version, types is [], rootDir is the directory of tsconfig.json, noUncheckedSideEffectImports is true, libReplacement is false), and options deprecated in 6.0 are hard errors in 7.0 (target es5, downlevelIteration, moduleResolution node10 (alias node) and classic, module amd, umd, system and none, baseUrl, outFile, esModuleInterop or allowSyntheticDefaultImports set to false, alwaysStrict set to false, the module keyword for namespaces, asserts on imports, /// <reference no-default-lib="true"/> directives). Every card about a default or a removed option names the version inside the statement ("Since TypeScript 6.0, ...", "In TypeScript 7.0, ...") and in "appliesTo". Cards about type-system behaviour leave the version out of the statement and set "appliesTo" to "TypeScript 6.0 and 7.0". Never describe 5.x behaviour as current: strict is no longer off by default, and node10 is no longer a usable moduleResolution value.
- Known differences between 6.0 and 7.0 for .ts files: template literal type inference with infer on an empty placeholder takes a full Unicode code point in 7.0 (a UTF-16 code unit in 6.0), and in 7.0 conflicting declarations error at every contributing site even under skipLibCheck. Write no card whose answer depends on either; in particular, no template literal example with emoji or other non-BMP characters, and no skipLibCheck card about conflicting declarations.
- Configuration assumed by every card: the TypeScript 6.0 and 7.0 defaults, so strict (and with it strictNullChecks) is on, and noUncheckedIndexedAccess and exactOptionalPropertyTypes are off. A card whose answer depends on a different setting names that setting in the statement. The assignability table on the Type Compatibility page marks some cells as compatible only when strictNullChecks is off: under the assumed configuration those pairs are not assignable.
- Leave out: the exact default target value (it floats, es2025 today), performance figures for TypeScript 7.0, package download counts, nightly builds, experimental or preview features, the stableTypeOrdering flag, legacy experimentalDecorators, namespaces beyond the removal of the module keyword, triple-slash path references, and type checking of JavaScript files with JSDoc (it was reworked in 7.0). At most one card in the deck may cover TypeScript 7.0 tooling (its tsc binary, the @typescript/typescript6 package and tsc6, no programmatic API in 7.0), and it gets "volatility": "may_change".
- Traps to test with care: strictFunctionTypes checks parameters of function-type syntax but leaves method syntax bivariant; noUncheckedIndexedAccess and exactOptionalPropertyTypes are outside the strict family; excess property checks apply only to fresh object literals; satisfies checks a value without changing its inferred type while an annotation does change it; as and ! are erased and do no runtime check; conditional types distribute only when they act on a generic type given a union, and wrapping both sides of extends in square brackets turns that off; string enum members get no reverse mapping; const enums inline their values and ambient const enums are incompatible with isolatedModules; enums are not erasable syntax, so erasableSyntaxOnly rejects them (as it does parameter properties); type aliases cannot be reopened while interfaces merge; unknown accepts every value but allows no operations until narrowed; nothing except never is assignable to never; since 6.0 paths work without baseUrl, and baseUrl is no longer a look-up root.
- Never state a judgement as a fact. The handbook says that in modern TypeScript you may not need an enum when an object with as const could suffice; it does not say enums are wrong. Write about what each construct does, not which one is best.
- Overlap with other decks: no React or JSX typing (react-fundamentals, nextjs-rendering), no generic JavaScript runtime facts that are not about TypeScript (for example how typeof null behaves may appear only as a narrowing pitfall the handbook names), and nothing about security (web-security).
- Names: write compiler options exactly as the TSConfig reference does (camelCase, for example noUncheckedIndexedAccess), option values in lower case as the docs write them (nodenext, bundler, preserve, esnext), and utility types with their exact names and type parameters as the Utility Types page shows them (for example Record<Keys, Type>, Exclude<UnionType, ExcludedMembers>).
