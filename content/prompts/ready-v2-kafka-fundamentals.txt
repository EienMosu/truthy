- Ordering traps: ordering holds only within a partition; the same key goes to the same partition only while the partition count is unchanged; with enable.idempotence=false, retries and more than one in-flight request can reorder records, while idempotence preserves order for up to 5 in-flight requests. A record without a key is not sent round-robin by default: the default logic sticks to one partition until at least batch.size bytes are produced, and RoundRobinPartitioner is a separate class.
- Idempotence trap, verified: idempotence is on by default only when no conflicting setting is present. acks other than all or retries=0 silently turn default idempotence off, and the same settings with enable.idempotence=true set explicitly raise a ConfigException. max.in.flight.requests.per.connection above 5 is different: since 4.0 it no longer silently turns idempotence off (4.0 upgrade notes), so the producer refuses that configuration unless enable.idempotence=false is set explicitly. The enable.idempotence entry on the 4.3 producer config page still states the generic "idempotence is disabled" rule for any conflicting setting: never use that sentence for the max.in.flight case, and write at most one card on the max.in.flight case, citing the 4.0 upgrade notes and the max.in.flight.requests.per.connection entry.
- Delivery semantics traps: Kafka's default is at-least-once; auto commit gives at-least-once only if all records from a poll are processed before the next poll or close; read_uncommitted, the default isolation level, returns records of aborted transactions; exactly-once with plain clients needs a transactional producer plus read_committed consumers with enable.auto.commit=false, and exactly-once to an external system needs that system's cooperation. The idempotent producer alone removes duplicates caused by its own retries; it does not make a consume-process-produce loop exactly-once. Transaction markers occupy offsets, so consumers see offset gaps in both isolation levels; never write that read_uncommitted consumers see contiguous offsets on a transactional topic. Kafka Connect exactly-once depends on the connector: no card says Connect makes every connector exactly-once.
- Group membership traps: when max.poll.interval.ms is exceeded, a dynamic member leaves the group and its partitions are reassigned, but a static member (group.instance.id set) stops heartbeating and its partitions are reassigned only after the session timeout; state which kind of member a card means. With the Streams rebalance protocol, static membership and regular expression subscriptions are not supported in 4.3.
- Retention and compaction traps: retention deletes whole segments, never single records; the active segment is never compacted; retention.bytes is per partition; compaction keeps at least the last value per key, never reorders, and never changes offsets; a tombstone is a key with a null value and is itself removed after delete.retention.ms; per-topic settings use the topic names (cleanup.policy, retention.ms), while the design page's example uses the broker default name log.cleanup.policy: keep topic and broker names straight. With CreateTime, the broker rejects records whose timestamp is too far in the future (message.timestamp.after.max.ms, lowered in 4.0): never write that a CreateTime topic accepts any producer timestamp.
- Known inconsistencies in the official pages, verified on 2026-10-08; write no card that rests on the inconsistent wording: (1) the design page says "reads can go to the leader or the followers", while replica.selector.class defaults to an implementation that returns the leader: cards say consumers fetch from the leader by default, and no card describes follower fetching setup. (2) The KafkaConsumer javadoc says the client "can communicate with brokers that are version 0.10.0 or newer", while the 4.0 upgrade notes require brokers and clients of version 2.1 or higher: no card on client and broker version compatibility. (3) The design page says static membership needs brokers and clients on 2.3 or later, while the KIP index lists KIP-345 under 2.4.0: no card on the release that introduced static membership. (4) The KIP index is stale for KIP-966, KIP-853, KIP-890, KIP-1030, KIP-1071 and KIP-1274: take landing releases from the kafka.apache.org upgrade notes and operations pages. (5) The 4.3 docs contain no Schema Registry and no schema compatibility rules: "schema" cards test only what kafka.apache.org states, namely that brokers store keys and values as bytes, clients serialize and deserialize them, and Kafka Connect converters with schemas.enable carry Connect schemas; no card about Avro, Protobuf, JSON Schema compatibility modes or any registry. (6) The enable.idempotence entry versus the 4.0 note on max.in.flight.requests.per.connection: see the idempotence trap.
