No card may present assignment to a typed variable as new in Go 1.27, and `x := sum` with no type information stays illegal.
- Struct literal trap (r5), verified in the spec Struct literals section and the go1.27 blog post: the key is the promoted field's own name, as in the spec example Line{name: "diagonal"} and the blog example Gopher{Burrow: ...}; write no card with a dotted key, no card where reaching the field crosses an embedded pointer (illegal), and remember that setting both an embedded struct and one of its fields in the same literal is illegal.
- Loop traps (r9), verified in the spec For statements section and the loopvar blog post: each iteration of a three-clause loop and of a range loop with := has new variables; in a three-clause loop the new variable is initialized from the previous iteration's value before the post statement runs (the spec example prints 1 3 5); the old semantics still apply to packages in modules whose go line is older than 1.22; the range expression is evaluated once before the loop, but not at all when at most one iteration variable is present and x or len(x) is constant; range over an integer n of an untyped constant gives int iteration values, and n <= 0 runs no iterations; for a range-over-function loop, yield returns false when the loop body stops early, the spec says yield must not be called again, and the iter package says yield panics if it is; a range loop over an array or slice with only the index variable does not index the elements; range over a nil slice or nil map runs zero iterations, while range over a nil channel blocks forever (r11).
- Interface and method traps (r6, r7), verified in the spec and the FAQ: an interface value is nil only when both its dynamic type and value are unset, so returning a nil *MyError as an error gives a non-nil error; comparing two interface values whose identical dynamic type is not comparable panics at run time; a type assertion or type switch needs an interface operand, not a type parameter; fallthrough is not permitted in a type switch; in a case listing several types the switch variable has the type of the guard expression; the method set of T holds only value-receiver methods while *T holds both, so a T stored in an interface does not satisfy an interface that needs a pointer-receiver method, while t.M() on an addressable t is shorthand for (&t).M(); map elements are not addressable, so a pointer method cannot be called on m[k] directly; a type defined from another type does not inherit the methods bound to that type, but the spec says the method set of an interface type or of elements of a composite type stays unchanged, so a defined struct type keeps the methods promoted from its embedded fields: no card may say a defined type never has its source type's methods.
- Slice, map and string traps (r2, r3, r4), verified in the spec, the blog posts and pkg.go.dev: append reuses the underlying array when the capacity suffices, so two slices appended from the same base may overwrite each other; never write a card about the exact growth amount of append (implementation detail); a full slice expression caps the capacity so the next append allocates; a nil slice and an empty slice both have length 0 but only the nil slice compares equal to nil, while slices.Equal considers nil and empty slices equal and slices.Clone preserves nilness (no card on how encoding/json renders them); map iteration order is "not specified and is not guaranteed to be the same from one iteration to the next": say that, never "random" or "randomized on purpose"; writing to a nil map panics while reading returns the zero value; the FAQ says map access is unsafe only when updates are occurring, so concurrent reads alone are safe: no card may say any concurrent map access is unsafe, and no card on whether the runtime detects concurrent map writes or on recovering from that failure; len of a string counts bytes and range over a string yields runes at byte offsets; string(65) is "A", not "65" (the spec keeps this conversion "for historical reasons", notes it may eventually be removed and that go vet flags certain such conversions: at most one card, testing the language rule only).
- Arithmetic traps (r1), verified in the spec Arithmetic operators section: integer division by zero panics at run time and a constant zero divisor is a compile error; integer overflow wraps without a panic; write no card on floating-point division by zero at run time, whose result the spec leaves to IEEE 754 with any panic implementation-specific.
- Defer, error and panic traps (r8, r10), verified in the spec, pkg.go.dev and Effective Go: the arguments of a deferred call are evaluated when the defer statement executes, not when the call runs; deferred calls run after return has set the result parameters, so a deferred closure can change a named result; errors.New returns a distinct value for every call even with the same text, so two such errors are not equal; %w wraps and %v does not; fmt.Errorf with several %w verbs returns an error with Unwrap() []error, which errors.Unwrap does not unwrap (it calls only Unwrap() error); errors.Is requires a comparable target; errors.As panics when its target is not a non-nil pointer to a type that implements error or to an interface type; the errors docs say "For most uses, prefer AsType"; errors.Join returns nil when every argument is nil; recover returns nil unless it is called directly by a deferred function while the goroutine is panicking; an unrecovered panic terminates the program even if it happens in a goroutine other than main, and recover in another goroutine cannot stop it; the Go 1.25 notes describe a compiler fix that makes code using a result before checking its error (f.Name() on a nil *os.File) panic as the spec requires: at most one card, set "volatility" to "stable" and phrase it as the spec behaviour, not as compiler history.
- Concurrency traps (r11, r12), verified in the spec, the Memory Model and pkg.go.dev: when main returns the program exits without waiting for other goroutines; sending on a closed channel, closing a closed channel and closing a nil channel panic, while receiving from a closed channel never blocks; communication on a nil channel blocks forever; select picks among ready cases by uniform pseudo-random selection, so source order gives no priority; the Memory Model's "Don't be clever" advice and its happens-before rules for channels may be tested only as the page states them, and no card may claim that a racy program is safe because one machine word is written; a Mutex or WaitGroup must not be copied after first use; a locked Mutex is not associated with a goroutine, so another goroutine may unlock it; RWMutex forbids recursive read locking; the function passed to WaitGroup.Go must not panic; Add calls with a positive delta that occur when the counter is zero must happen before Wait, while other Add calls may happen at any time; Once.Do treats a panic in f as a return, so f is never called again; context cancellation flows from parent to derived contexts, never upward; Background's Done may return nil; WithValue keys should not be of type string or another built-in type; failing to call a CancelFunc leaks the derived context until the parent is canceled.
- Generics traps (r13), verified in the spec: interfaces that are not basic (with type elements such as ~int | ~string, or embedding comparable) can only be used as constraints, never as the type of a variable; any is an alias for interface{}; ordinary interface types satisfy comparable as type arguments even though they are not strictly comparable (Go 1.20), and the spec says they satisfy but do not implement it; since Go 1.26 a generic type may refer to itself in its type parameter list (type Adder[A Adder[A]] interface); write no card about core types, which the spec removed in Go 1.25 in favour of dedicated prose.
- Package and module traps (r14), verified in the spec, pkg.go.dev/cmd/go and the modules references: exported means the first character is a Unicode upper-case letter and the name is declared at package level or is a field or method name, so a lower-case name is visible in every file of its package; an internal directory is importable only by code rooted at its parent; multiple init functions per file are allowed and none can be called or referred to; the go.mod reference says that since Go 1.21 "Go toolchains refuse to use modules declaring newer Go versions" and that the go directive is an input into selecting which toolchain to run: by default the go command may switch to a newer toolchain, so no card may claim that building such a module with default settings simply fails; a module at major version 2 or higher ends its module path with /vN, and the suffix is not allowed at v0 or v1 (leave out the gopkg.in special case and +incompatible versions). Leave out GOPATH mode, vendoring, workspaces, GOPROXY and the checksum database beyond naming go.sum, GOTOOLCHAIN switching details, tool directives, the ignore directive, godebug lines and the go mod tidy require-block merging of Go 1.27.
- Leave out entirely: unsafe, cgo, reflect, runtime internals, the scheduler, the garbage collector (Green Tea in 1.26) and escape analysis or stack allocation of slices, GOMAXPROCS defaults (container-aware since 1.25), performance figures, size-specialized allocation, the goroutine leak profile, encoding/json and encoding/json/v2 (new in 1.27, with v1 now backed by the v2 implementation), net/http, crypto and crypto/mldsa, the new uuid package, simd and simd/archsimd, runtime/secret, anything enabled by GOEXPERIMENT, time.Timer and Ticker channel semantics (changed in 1.23, GODEBUG asynctimerchan removed in 1.27), testing, testing/synctest and B.Loop, go fix modernizers, go doc, gofmt and go vet analyzer names (a card may say "go vet reports ..." only where the cited page says so), struct field alignment, the swiss table map implementation, Unicode version upgrades, and the golang.org/x repositories.
