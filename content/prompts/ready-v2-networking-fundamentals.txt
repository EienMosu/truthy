Examples verified on 2026-10-08: RFC 9293 says an actively closed connection MUST linger in TIME-WAIT for 2 x MSL, SHOULD implement Nagle and MUST let an application disable it per connection, MAY include keep-alives and, if it does, MUST default them to off; RFC 9293 SHOULD generate initial sequence numbers as a clock plus a keyed function; RFC 6298 says an RTO below 1 second SHOULD be rounded up; RFC 4787 says a NAT MUST have Endpoint-Independent Mapping (for UDP); RFC 9846 says each following certificate SHOULD certify the one before it, a trust anchor MAY be omitted and clients SHOULD send server_name when the server is identified by name.
- Version pinning: cite only current RFCs. Never cite or teach from an obsoleted RFC: RFC 793, RFC 6528 and RFC 6093 (use RFC 9293), RFC 8446 and RFC 5246 (use RFC 9846), RFC 3315 and RFC 8415 (use RFC 9915), RFC 4941 (use RFC 8981), RFC 1519 (use RFC 4632), RFC 6125 (use RFC 9525), RFC 7719 and RFC 8499 (use RFC 9499), RFC 7042 (use RFC 9542), RFC 6874 (use RFC 9844), RFC 2460 (use RFC 8200), RFC 1981 (use RFC 8201), RFC 2463 (use RFC 4443), RFC 3513 (use RFC 4291), RFC 2461 and RFC 2462 (use RFC 4861 and RFC 4862), RFC 5735 (use RFC 6890), RFC 8312 (use RFC 9438), RFC 6555 (use RFC 8305), RFC 3484 (use RFC 6724), RFC 1393 (Historic). Write no card whose point is an RFC number, a publication year, an RFC status, a STD or BCP number, or a rename. Set "appliesTo" to the RFC or registry the card rests on.
- TLS traps: TLS 1.3 is now RFC 9846 (July 2026), a minor update of RFC 8446 with the same version number, which among other changes forbids negotiating TLS 1.0 and 1.1, forbids reusing key shares between connections and uses KEM-neutral wording for key exchange; never cite RFC 8446. RFC 9846 also obsoletes RFC 5246, the TLS 1.2 document, but TLS 1.2 itself is not deprecated: RFC 9851 freezes new TLS 1.2 features and RFC 9852 says new protocols that use TLS must require TLS 1.3; no card says TLS 1.2 is deprecated, forbidden or retired. In the full TLS 1.3 handshake the client sends its first application data (RFC 9846 calls it 1-RTT data) after one round trip of TLS; over TCP the TCP handshake adds its own round trip, so a round-trip card must say whether it counts TCP. Write no card on how many round trips TLS 1.2 needs (RFC 9846 does not state it). MDN's "How browsers work" page (last modified December 18, 2025) says the TLS negotiation "requires five more round trips" and speaks of "eight round trips" before the first request: that is wrong for TLS 1.3, so never cite that page for round-trip counts, and treat that claim as a misconception a false card may correct. 0-RTT data has no forward secrecy guarantee and no guarantee against replay between connections. In TLS 1.3 the server certificate is encrypted, but the ClientHello, including SNI and ALPN, is sent in the clear unless Encrypted Client Hello is used; ECH (RFC 9849, March 2026) is new: test only what the RFC defines, never browser or server support, and give any ECH card "volatility": "may_change". SNI carries a DNS host name and literal IP addresses are not permitted in it (RFC 6066). RFC 9525 says the Common Name must not be used to identify a service, so no card may say clients check the CN; when wildcards are supported, there is one wildcard, it is the complete left-most label and it matches exactly one label. Certificate chain order: the sender's certificate MUST come first, but each following certificate only SHOULD certify the one before it: no card says the order of the rest is mandatory. No card on cipher suite names, key sizes, post-quantum hybrids (RFC 9954, RFC 10024), OCSP, Certificate Transparency or certificate lifetimes.
- TCP traps: TIME-WAIT is held by the side that closes first (the active closer), which can be the client or the server; RFC 9293 lets it accept a new SYN to reopen the connection from TIME-WAIT under conditions, so no card says a connection in TIME-WAIT can never be reused. MSL is 2 minutes in RFC 9293, but implementations use other values, so write no card on the TIME-WAIT duration in seconds; test 2 x MSL and the two reasons (a lost final ACK and delayed segments of an old connection). Initial sequence numbers do not start at zero; RFC 6528 is obsoleted, cite RFC 9293 Section 3.4.1. The connection teardown is a FIN and an ACK in each direction (MDN calls it a four-way handshake; the FIN and ACK of one side can share a segment, so no card claims exactly four segments are always sent); RFC 9293 lets a host implement a half-duplex close in which the closing application cannot read further data, so a half-close card says the other side can still send. SYN and FIN consume sequence numbers; a pure ACK does not. Keep-alives are optional (MAY) and off by default where implemented. CUBIC being the default in Linux, Windows and Apple stacks comes from the RFC 9438 abstract: say "RFC 9438 says" and set "volatility": "may_change". Slow start grows the congestion window quickly (up to one SMSS per ACK, roughly doubling per round trip); no card may say slow start grows it slowly or linearly. Write no card on RTO, delayed-ACK, initial window or retransmission counts as numbers, and none on BBR, ECN, L4S, AccECN, TCP Fast Open (Experimental) or MPTCP.
- UDP and ports traps: the UDP checksum is optional over IPv4 and required over IPv6, except for the tunnel exception in RFC 8200; UDP options (RFC 9868) are new: no cards. RFC 6335 names the ranges System (Well Known) 0-1023, User (Registered) 1024-49151 and Dynamic (Private or Ephemeral) 49152-65535 and says Dynamic Ports are never assigned; operating systems choose their own ephemeral ranges (Linux, for example, uses a different default), so write no card on an operating system's ephemeral range and none claiming every system picks source ports from 49152-65535. Since RFC 6335, IANA assigns a port only for the transport protocols requested and marks it Reserved in the others; older assignments often cover both TCP and UDP: no card claims every assignment covers both. Do not use the term "5-tuple" as an RFC term; none of the pinned RFCs defines it. The MDN Port glossary page says each port below 1024 "is associated by default with a specific protocol": do not cite it. An assigned port does not prove that traffic on it is that service (RFC 6335 Section 8).
- Addressing and link traps: classful addressing is obsolete (RFC 4632); no card may present Class A, B or C as how addresses are allocated or routed today, and a card may mention classes only as the legacy plan CIDR replaced. 172.16.0.0/12 runs from 172.16.0.0 to 172.31.255.255; 100.64.0.0/10 is Shared Address Space for carrier-grade NAT and not an RFC 1918 range; 169.254.0.0/16 is link-local and not forwardable. A /31 has no network or broadcast address on a point-to-point link (RFC 3021), so the "subtract two addresses" rule is not universal; cloud providers reserve extra addresses per subnet, which belongs to the cloud decks: no cloud-specific cards. NAT is an address-sharing technique: write no card claiming it is or is not a security control or firewall; RFC 4787 states behavioural requirements for unicast UDP, so its cards say UDP. ARP (RFC 826) is a generic protocol-address resolution protocol, not defined only for IPv4; IPv6 does not use it. RFC 894's text says "minimum length ... is 1500 octets" by mistake (verified errata 570 and 5141 correct it to maximum): a 1500-octet card says maximum and cites the erratum. Ethernet itself is an IEEE standard: Ethernet facts stay within what RFC 894, RFC 826, RFC 9542 and RFC 2464 state.
- IPv6 traps: there is no broadcast in IPv6; every interface has a link-local address; ARP does not exist in IPv6 (Neighbor Discovery over ICMPv6 takes over its job). RFC 4291 defines Global Unicast as everything not otherwise listed, while IANA assigns unicast only from 2000::/3 today: word cards as one or the other source does. ULAs have global scope by default (RFC 4193) but are not globally reachable (IANA registry, which notes they are drawn from the Global Unicast range but not globally routed): never call them link-local or site-local, and never call them publicly routable. Site-local fec0::/10 is deprecated. RFC 4291 still says interface identifiers are built in Modified EUI-64 format, but RFC 7136 makes them opaque and RFC 8064 recommends stable identifiers per RFC 7217 instead of embedding the MAC address: no card may say SLAAC addresses contain the MAC address or reveal it by design. SLAAC needs prefix length plus interface identifier length to equal 128 (64-bit identifiers on Ethernet, RFC 2464): no card claims SLAAC works with any prefix length. Duplicate Address Detection is skipped when DupAddrDetectTransmits is zero and never done for anycast: no card claims every address is always checked. Hosts learn default routers from Router Advertisements (RFC 4861); write no card claiming DHCPv6 does or does not deliver a default route. The IPv6 documentation prefixes are 2001:db8::/32 and, since RFC 9637, 3fff::/20: no card claims 2001:db8::/32 is the only one. IPv6 zone identifiers in URIs (RFC 6874) were obsoleted by RFC 9844: no cards on zone identifiers in URLs.
- ICMP and MTU traps: ICMP is part of the internet layer although it is carried inside IP; blocking Fragmentation Needed or Packet Too Big breaks Path MTU Discovery and causes black holes (RFC 1191; RFC 4890, an Informational document, lists Packet Too Big among traffic that must not be dropped). Routers never fragment IPv6 packets; IPv4 routers fragment unless Don't Fragment is set. Classic traceroute as RFC 2151 (Informational) describes it uses UDP probes to an invalid port; other implementations use ICMP Echo or TCP: cards say "classic traceroute" and test only the TTL and Time Exceeded mechanism, never a tool's default protocol, flags or output. RFC 791 defines TTL in seconds with each module decrementing it by at least one; in practice it works as a hop count and IPv6 renamed it Hop Limit: no card says TTL is a time in seconds without that context. Fixed values that may each be tested once: the 1500-octet Ethernet maximum (RFC 894 with its errata), the 1280-octet IPv6 minimum MTU, the 68-octet and 576-octet IPv4 minimums, the 1200-byte QUIC Initial datagram size.
- DNS traps: a CNAME cannot sit at a zone apex because a name with a CNAME has no other data and the apex has SOA and NS records; RFC 2181 allows DNSSEC records next to a CNAME, so no card says a CNAME name can hold no record of any other type at all. "ALIAS", "ANAME" and "CNAME flattening" are provider features, not standard record types: no card names them. RFC 9460 offers CNAME-like apex aliasing through SVCB or HTTPS records in AliasMode for the protocols that use those records, not for every protocol; client support is not tested, and HTTPS records as a way to discover HTTP/3 or Alt-Svc belong to http-fundamentals. MX and NS targets must not be aliases (RFC 2181). A lower MX preference value is preferred. RFC 7766 requires all general-purpose DNS implementations to support TCP, so the common claim that DNS uses TCP only for zone transfers is wrong; no card says DNS uses only UDP. The 512-byte limit applies to UDP messages without EDNS(0). The IANA page describes the root servers as "a network of hundreds of servers" configured as "13 named authorities" (a to m, run by 12 organizations): never say "13 root servers" as machines. A record may be served after its TTL under serve-stale (RFC 8767), so no card says resolvers never return expired data. Negative answers are cached for the minimum of the SOA MINIMUM field and the SOA record's TTL (RFC 2308). Use RFC 9499 terms: stub resolver, recursive resolver, authoritative server; the MDN "How browsers work" page says a phone's lookup goes to "an authoritative DNS server", which skips the recursive resolver: do not cite it for resolution. The MDN TTL glossary page says a TTL is part of an HTTP response header: do not cite it. No cards on DNSSEC beyond naming it, record TTL maximums, label or name length limits, zone transfer details, DNS cookies or resolver software.
- Routing traps: longest-match forwarding decides before any metric, so a /24 route beats a /16 route and both beat the default route; forward and return paths can differ. BGP chooses routes by local policy; AS_PATH length is one step of the decision process, not a shortest-path metric: no card says BGP always picks the shortest AS path or the lowest latency. BGP listens on TCP port 179. Since RFC 8212, routes from or to an EBGP peer are not used or advertised without an explicit policy. No cards on OSPF, IS-IS, RIP internals, BGP attribute order in the decision process, communities, RPKI or route reflectors beyond naming.
- MDN: MDN may be cited only for how a browser sequences DNS, TCP and TLS before the first request and for the browser view of QUIC, and never for a protocol fact the RFCs define. Known MDN problems verified on 2026-10-08: the TLS glossary page (November 30, 2025) still links RFC 8446 and the SSL glossary page (November 30, 2025) says "The current version of SSL is version 3.0" (SSL 3.0 is deprecated by RFC 7568); the IPv4 glossary page (July 11, 2025) blames IPv4's "security problems"; the Port and TTL glossary pages (July 11, 2025) are imprecise; the How browsers work page miscounts TLS round trips. A card about browser behaviour says "browsers" or "MDN says" and gets "volatility": "may_change".
- Never state a judgement as a fact. A recommendation may be tested only as the RFC words it, for example "RFC 8064 recommends stable interface identifiers that do not embed the MAC address", "RFC 1918 says routing information about private networks shall not be propagated on inter-enterprise links", "RFC 9852 says new protocols that use TLS must require TLS 1.3". Deployment facts (IPv6 adoption, which stacks use CUBIC, which browsers use ECH or QUIC) get "volatility": "may_change" and the source's own wording, or are left out.
