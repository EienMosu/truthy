You are writing content for "Truthy", a mobile true/false card game that teaches IT knowledge. The player sees one statement, answers True or False, then reads a short explanation. A wrong fact in this game teaches people something false, so accuracy matters more than volume.

DECK
Tailwind CSS for working frontend developers: utility-first styling, CSS-first configuration, design tokens, variants, source detection, custom styles and migration from v3.
Taxonomy: frontend > CSS > topics > Tailwind CSS. This is a documentation deck with sections grouped from the [official Tailwind CSS documentation](https://tailwindcss.com/docs/). Pin the current major, Tailwind CSS v4; the [official site](https://tailwindcss.com/) and documentation display v4.3 on 2026-10-08. CSS language semantics belong to css-fundamentals.

RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: a frontend developer who uses Tailwind in production. Test what Tailwind generates or configures: how a token changes its API, which condition a variant targets, what a directive expands or registers, why a class is missed, and what migration changes in an existing project. Short class or CSS fragments may give context. Avoid utility-to-property lookup quizzes, palette and breakpoint memorization, installation command spelling, performance benchmarks and design opinions.
- Assumed context: Tailwind CSS v4 using the verified v4.3 docs, CSS-first configuration, the default theme, default variants and automatic source detection, with Preflight included, unless the statement specifies a customization. Assume browsers support the CSS features in the example. Name customized selectors, import options, reference contexts or detection paths when they decide the answer. For conflicting utilities, specify comparable active conditions, importance and specificity rather than treating stylesheet order as a universal override rule.
- Version pinning: use "Tailwind CSS v4" in appliesTo for facts verified across the major, and "Tailwind CSS v4.3" for facts verified only in the current baseline. Migration-sensitive statements name v4 inside the statement. Do not infer that a current feature existed in v4.0, or invent the minor release that introduced it. Keep v3 behavior in explicit migration context; release numbers and renamed spellings are not card topics.
- Theme boundary: @theme establishes Tailwind APIs as well as CSS variables; :root alone does not register matching utilities. Keep inline's emitted-value behavior distinct from static's variable-emission behavior, and distinguish removing a theme namespace from removing static utilities. Test token sharing and use as Tailwind behavior, leaving general var() resolution and inheritance to CSS. [Theme variables](https://tailwindcss.com/docs/theme).
- Variant traps: v4 hover includes a hover-capability condition; state its primary-input condition when it decides the answer. Default dark follows prefers-color-scheme, while a selector override makes application state control activation. A peer marker precedes its target sibling; named groups and peers need no configuration. Built-in boolean ARIA variants match "true"; data presence and value matching differ. These variants style existing state. [States](https://tailwindcss.com/docs/hover-focus-and-other-states), [Dark mode](https://tailwindcss.com/docs/dark-mode).
- Responsive traps: sm: is a minimum viewport breakpoint, and unprefixed utilities supply the small-screen starting styles. Viewport breakpoints and container sizes use separate theme namespaces; named containers select the intended ancestor. Include @container-size only under the verified v4.3 baseline. Test Tailwind's markers, variant ranges and configuration, leaving containment algorithms and query-unit semantics to CSS. [Responsive design](https://tailwindcss.com/docs/responsive-design).
- Detection traps: Tailwind scans text rather than evaluating templates; dynamically selecting complete class strings differs from assembling class fragments. Automatic scanning excludes dependencies and CSS files. @source paths are stylesheet-relative, while automatic detection starts at the working directory unless its base is set. Safelisting uses @source inline(); static theme-variable emission does not safelist utilities. [Source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files), [Theme variables](https://tailwindcss.com/docs/theme).
- Extension traps: v4 @layer is native CSS layering, not utility registration; @utility creates variant-enabled utilities. @apply inlines existing utilities into a rule. Functional utilities resolve accepted values and omit unresolved declarations; test the resulting output rather than memorizing accepted type names. @variant applies a condition within CSS; @custom-variant defines a reusable condition. @reference supplies definitions to a separately processed stylesheet without duplicating emitted styles; customized projects reference their main stylesheet. [Custom styles](https://tailwindcss.com/docs/adding-custom-styles), [Directives](https://tailwindcss.com/docs/functions-and-directives).
- Verified migration traps: JavaScript configuration is loaded explicitly through @config; CSS definitions merge where possible and otherwise take precedence. corePlugins, safelist and separator are unsupported legacy options. @plugin remains a compatibility route; theme() is deprecated and resolveConfig was removed. Gradient variants preserve untouched stops; default border and ring colors use currentColor; transform-none leaves individual transforms to their own reset utilities. Reserve spacing/divide selector changes and removed container center/padding configuration for r12. [Directives](https://tailwindcss.com/docs/functions-and-directives), [Upgrade guide](https://tailwindcss.com/docs/upgrade-guide).
- Stale-material guardrails: @tailwind directives and deprecated opacity utilities were removed; current entry CSS uses @import. The leading important modifier remains compatible but deprecated; use the trailing form. CSS-variable shorthand now uses parentheses. Shadow, radius and blur names changed; avoid old scale assumptions and rename-only cards. Stacked variants apply left to right. Assign these behaviors to their owning sections rather than repeating them in migration. [Upgrade guide](https://tailwindcss.com/docs/upgrade-guide).
- Documentation example trap: the upgrade guide's direct-variable component example uses --text-red-500 for color; the theme reference defines colors under --color-*. Use --color-red-500 and verify generated-CSS examples rather than inheriting that typo. [Theme variables](https://tailwindcss.com/docs/theme), [Upgrade guide](https://tailwindcss.com/docs/upgrade-guide).
- Preflight and tooling: name Preflight when testing its resets; they are Tailwind defaults, not CSS language defaults. Build integration cards test compilation responsibilities and separately processed stylesheet context, not package-name recall. Attribute preprocessor limitations to Tailwind's documented workflow; omit numeric browser-support minima and claims that every supported utility works in every browser. [Preflight](https://tailwindcss.com/docs/preflight), [Compatibility](https://tailwindcss.com/docs/compatibility).
- Overlap: css-fundamentals owns the cascade algorithm, specificity, inheritance, selectors, custom-property semantics, units, layout, media queries and container-query mechanics. Here those are assumed context and the decisive fact concerns Tailwind's API, generated output or defaults. web-accessibility owns ARIA meanings, focus requirements and contrast; test only Tailwind variant matching. Framework decks own component behavior, rendering and CSS Modules semantics; r11 tests Tailwind reference visibility only. javascript-fundamentals owns interpolation and DOM APIs; r3 tests Tailwind detection. web-performance owns rendering cost and loading optimizations.
