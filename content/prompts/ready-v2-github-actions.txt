RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: intermediate, for DevOps engineers and developers who write and run workflows every week. Test behaviour and syntax that decides whether a workflow works: which event triggers what and on which ref, what a context or expression evaluates to and when, where a key is valid (workflow, job or step level), what a file such as GITHUB_ENV, GITHUB_OUTPUT or GITHUB_STEP_SUMMARY does, what a permission or policy allows, and which level (enterprise, organization, repository, environment) a setting lives at. Assume the player knows what CI/CD is; leave out cards that only define a workflow, a job or a runner.
- Never state a judgement as a fact. "X is best practice" is acceptable only when docs.github.com says it in those terms (for example pinning an action to a full-length commit SHA, granting the GITHUB_TOKEN the minimum required permissions, or passing untrusted input to an inline script through an intermediate environment variable). Prefer statements about what a feature does.
- Keep overlapping bullets apart. The guide repeats several topics across sections; test each in one place only: YAML anchors and matrix syntax in 1.2, their interpretation and selective reruns of matrix jobs in 2.1; caching, artifacts and retention mechanics in 1.3, cost and scaling trade-offs in 5.2; environment protections and status badges in 1.3, approval gates and required reviewers as a security control in 5.1; workflow commands inside workflows in 1.2, inside actions (and the actions/toolkit side) in 3.2; reusable workflow syntax (workflow_call, inputs, secrets, outputs) in 1.1 and 1.3, the choice between workflow templates, reusable workflows and composite actions in 2.3, enterprise governance of shared components in 4.1; secret and variable scoping and REST management in 4.3, GITHUB_TOKEN, OIDC and leak prevention in 5.1; action allow and block policies in 4.1 for configuration, in 5.1 at most once as a security control; immutable actions and version pinning at most once in 1.2, 3.1 and 5.1 together.
- YAML merge keys: the guide lists "merge <<" next to anchors and aliases, but docs.github.com documents only anchors (&) and aliases (*), and GitHub said when anchors shipped that merge keys (a YAML 1.1 type) are not supported. Write no card that says merge keys work in a workflow, and no card about merge keys at all unless a current docs.github.com page states their status.
- Renamed and changed features are the main trap of this topic; never present an old behaviour as current. The guide says "starter workflows"; the docs say "workflow templates" (the old name survives only in the actions/starter-workflows repository name): use "workflow templates" in statements. YAML anchors and aliases, and workflow templates from internal or private .github repositories, became supported in September 2025; older material says the opposite. Since December 2025, pull_request_target always takes the workflow file and checkout ref from the default branch; older material says the pull request's base branch. actions/checkout refuses to fetch fork pull request code in pull_request_target and workflow_run workflows by default (v7, backported in July 2026); mark such cards "may_change". Node 20 was removed from GitHub Actions on September 23, 2026: JavaScript actions use runs.using: node24, even if a docs page still lists node20; write no card that presents node20, node16 or node12 as usable. The set-output and save-state workflow commands are replaced by GITHUB_OUTPUT and GITHUB_STATE; actions/upload-artifact and actions/download-artifact v3 and actions/cache v1 and v2 are retired. Ubuntu 20.04 images are retired, windows-latest moved to Windows Server 2025 and macos-latest to macOS 26: any card about a -latest label mapping is "may_change". Artifact attestation docs now use actions/attest; older material uses actions/attest-build-provenance.

Do not merge these three things into one card, and write a card on immutable actions or immutable releases only if a current docs.github.com page states the fact; mark it "may_change".
- Leave out numeric limits and values that GitHub has changed or may change: reusable workflow nesting depth and count, matrix job limits, cache size and eviction, artifact and log retention defaults and maximums, job and workflow timeouts, inactivity periods before scheduled workflows are disabled, concurrency limits, runner hardware sizes, minutes and prices. Test which setting controls a limit, not its value.
- Cards are about GitHub.com (GitHub Enterprise Cloud included). Leave out behaviour specific to GitHub Enterprise Server and anything the docs mark as public preview, including agentic workflows, even though the guide says the exam may ask about commonly used preview features. Features that became generally available in the last few months (workflow execution protections in September 2026, disabling standard hosted-runner labels in June 2026) may be tested only with "may_change".
