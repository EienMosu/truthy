RULES FOR THE STATEMENT
- Original wording. Do not copy or paraphrase practice exams, exam dumps or course material.
- One fact per statement. No compound statements where one half is true and the other false.
- Maximum 120 characters. Plain declarative sentence, present tense.
- No negations ("is not", "cannot", "never", "without") in the statement.
- No absolutes ("always", "all", "only", "every", "must") unless the official source states it that way.
- Use official product and API names exactly as the official source writes them today.
- A false statement is false for exactly one clear reason, and that reason is a realistic misconception a learner who studied could hold. Never make a statement false through trick wording, spelling or a changed number.
- No strawman: if nobody who studied would answer True, write a different card.
- No truism: a statement that is true by common sense, by definition or by arithmetic, and that is not specific to this subject, teaches nothing. Write a different card.
- No name giveaway: the answer must not be readable from the product name alone (for example "X for Windows File Server provides Windows file systems").
- True and false statements must be indistinguishable by form: within each section keep the average length of the false statements within 5 characters of the average length of the true ones, and use the same sentence patterns for both.
- No wording tells. A player who does not know the subject must not be able to guess from the words. Hedge verbs ("can", "supports", "lets", "allows", "may") must not mark true statements: use them about as often in false statements as in true ones. Requirement and coverage words ("requires", "must", "each", "every", "automatically", "by default", "directly") must not mark false statements: use them about as often in true statements as in false ones. Count them across the deck before every answer and rebalance.
- No recurring false-statement template, such as "X requires Y" where Y is optional, or "each X has its own Y": a template may carry at most two false statements in the whole deck.
- Write in your own words; do not reproduce a sentence of the official page with a word or two changed.
- Name the actor. No passive sentence whose answer depends on who does something ("a datacenter is selected" must say who selects it).
- The two sides of one distinction are one fact. If a card tests that A is X, no other card may test that B, the other side of the same two-way split, is Y (for example CapEx versus OpEx, horizontal versus vertical scaling).
- No strawman and no definition card: a statement whose answer follows from the meaning of a term in it (elastic, serverless, open standard, streaming) teaches nothing.
- Do not rely on facts that change often: prices, exact quotas and limits, counts of regions, free tier amounts, launch dates, preview features. If a card depends on something that could change within a year or two, set "volatility" to "may_change" and say why in "volatilityNote". Otherwise "stable".
- Leave out products that are deprecated, in maintenance mode or closed to new customers.
- Difficulty mix within each section: roughly 40% easy (1), 40% medium (2), 20% hard (3). Hard means a real distinction between two similar things, not an obscure detail.
- Depth: entry level (the exam page lists the experience level as Beginner; the exam is multiple choice). Test what each Kubernetes component and object does, how they relate, what happens in a common situation, and the cloud native concepts, projects and community structures the curriculum names. This is not the hands-on CKA: no YAML field spelling, no kubectl flag trivia, no numeric defaults (timeouts, ports, sizes, intervals, retention), no installation steps.
- The curriculum gives only competency names, so this deck sets the scope of each section as follows. This division is the deck's own, not the curriculum's; put each fact in the one section it belongs to.
- Scope of 1.1 Kubernetes Core Concepts: cluster architecture (control plane components kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager; node components kubelet, kube-proxy, container runtime), the declarative model and reconciliation by controllers, workload objects (Pod, ReplicaSet, Deployment, StatefulSet, DaemonSet, Job, CronJob), Namespaces, labels, selectors and annotations, init containers and sidecar containers.
- Scope of 1.2 Administration: kubectl and kubeconfig (clusters, users, contexts), the Kubernetes API (API groups, versions, resources, the API server as the single entry point), imperative versus declarative object management, resource requests and limits and the Pod QoS classes, ResourceQuota and LimitRange, extending the API with CustomResourceDefinitions and the operator pattern, cluster lifecycle at a conceptual level (kubeadm, version skew, upgrades, backing up etcd).
- Scope of 1.3 Scheduling: how kube-scheduler filters and scores nodes, the role of resource requests in placement, nodeSelector, node affinity, inter-pod affinity and anti-affinity, taints and tolerations, Pod priority and preemption, topology spread constraints, what happens to a Pod that no node can accept.
- Scope of 1.4 Containerization: containers versus virtual machines, Linux namespaces and cgroups, images, layers, tags versus digests, registries, the OCI image, runtime and distribution specifications, the Container Runtime Interface (CRI) and CRI runtimes (containerd, CRI-O), low-level runtimes (runc), RuntimeClass, image pull policy. Leave Dockerfile instructions, the docker CLI and Compose to the docker-fundamentals deck.
- Scope of 2.1 Networking: the Kubernetes network model (each Pod gets its own cluster-wide IP address, Pods reach each other without NAT), CNI plugins, Service types (ClusterIP, NodePort, LoadBalancer, ExternalName, headless Services), EndpointSlices, kube-proxy, cluster DNS (CoreDNS, Service DNS names), Ingress versus Gateway API, NetworkPolicy (and that it needs a network plugin that enforces it), service mesh concepts (data plane, control plane, mutual TLS between services).
- Scope of 2.2 Security: the path of an API request (authentication, authorization, admission control), RBAC (Role, ClusterRole, RoleBinding, ClusterRoleBinding), ServiceAccounts and their tokens, Secrets and encryption at rest, Pod Security Standards (Privileged, Baseline, Restricted) and Pod Security Admission, securityContext, the cloud native security lifecycle phases described on kubernetes.io. Leave web application vulnerabilities to the web-security deck.
- Scope of 2.3 Troubleshooting: reading the state of a cluster and its workloads: Pod phases, container states and restart policy, common failure states (Pending, CrashLoopBackOff, ImagePullBackOff, OOMKilled) and what causes each, events, node conditions and what happens to Pods on a node that stops reporting, liveness, readiness and startup probes and what each one does on failure, a Service whose selector matches no ready Pods.
- Scope of 2.4 Storage: ephemeral versus persistent volumes, emptyDir, ConfigMaps and Secrets mounted as volumes (the mount mechanism only; Secret security belongs to 2.2), PersistentVolume, PersistentVolumeClaim, StorageClass and dynamic provisioning, access modes, reclaim policies, the Container Storage Interface (CSI), volumeClaimTemplates in StatefulSets.
- Scope of 3.1 Application Delivery: Deployment rollout strategies (RollingUpdate, Recreate) and rollbacks, blue-green and canary as patterns built with tools on top of Kubernetes, Helm (charts, releases, values, repositories), Kustomize (bases, overlays, built into kubectl), GitOps and the four OpenGitOps principles (Declarative, Versioned and Immutable, Pulled Automatically, Continuously Reconciled), Argo CD and Flux, push-based CI/CD versus pull-based GitOps. Leave CI workflow syntax to the github-actions deck and infrastructure as code to the terraform-associate deck.
- Scope of 3.2 Debugging: the tools and techniques for investigating a running application: kubectl logs (including the logs of a previous container instance), kubectl describe, kubectl get events, kubectl exec, kubectl port-forward, kubectl debug and ephemeral containers, kubectl rollout status and rollout history, debugging Services and DNS from inside the cluster. A card about what a failure state means belongs to 2.3; a card about which tool or technique reveals it belongs here.
- Scope of 4.1 Observability: the telemetry signals (metrics, logs, traces), Prometheus (pull-based scraping, time series identified by metric name and labels, PromQL, exporters, Alertmanager), OpenTelemetry (API and SDKs, the Collector, signals, semantic conventions), the Kubernetes logging architecture (container stdout and stderr, node-level logging, no built-in cluster-wide log storage), the Metrics API and metrics-server (built for autoscaling, not for monitoring), distributed tracing concepts (spans, context propagation), SLIs and SLOs.
- Scope of 4.2 Cloud Native Ecosystem and Principles: the CNCF definition of cloud native, microservices versus monoliths, immutable infrastructure, declarative APIs, loose coupling and resilience, autoscaling at the level of what each autoscaler scales (HorizontalPodAutoscaler, VerticalPodAutoscaler, Cluster Autoscaler), serverless and Knative, why open interfaces (OCI, CRI, CNI, CSI) matter to the ecosystem (the details of each interface belong to its own section), the CNCF Landscape.
- Scope of 4.3 Cloud Native Community and Collaboration: CNCF and its place in the Linux Foundation, CNCF governance (Governing Board, Technical Oversight Committee, Technical Advisory Groups, end user community), project maturity levels (sandbox, incubating, graduated, archived) and how projects move between them, Kubernetes project governance (Steering Committee, SIGs, working groups, Kubernetes Enhancement Proposals, the release cycle and release team), the code of conduct, ways to contribute.
- Version pinning: pin the Kubernetes version from STEP 1. When a behaviour changed in a recent release, the statement says so (for example "Since Kubernetes v1.35, ...") and "appliesTo" carries it. Verified examples: dockershim was removed in v1.24 (the kubelet no longer talks to Docker Engine directly; images built with Docker still run on any CRI runtime); PodSecurityPolicy was deprecated in v1.21 and removed in v1.25, and Pod Security Admission is stable since v1.25; the Endpoints API is deprecated since v1.33 in favour of EndpointSlices; native sidecar containers (init containers with restartPolicy Always) are stable since v1.33; in-place Pod resize is stable since v1.35. Leave out alpha and beta features entirely (for example HorizontalPodAutoscaler scale to zero, beta and enabled by default in v1.37), and do not write a card that such a feature makes arguable (such as "an HPA cannot scale a Deployment to zero").
- Recent deprecations and removals, verified on kubernetes.io; respect them and do not teach the older behaviour as current: kube-proxy ipvs mode is deprecated since v1.35 (nftables is the recommended replacement on Linux); cgroup v1 support was removed in v1.35, so the kubelet fails to start on a node without cgroup v2; v1.35 was the last release to support containerd 1.x; the Service .spec.externalIPs field is deprecated since v1.36; kube-dns is deprecated in v1.37 (CoreDNS has been the default cluster DNS add-on since v1.13); the metrics.k8s.io Metrics API became stable (v1) in v1.37 after years in beta. Test only what is true in the pinned version, never planned future removal dates.
- Ingress trap: the Ingress API is generally available but frozen (no further changes, and no plans to remove it), and the Kubernetes project recommends Gateway API instead. Separately, the Ingress NGINX controller (kubernetes/ingress-nginx) is retired: best-effort maintenance ended in March 2026, its repository is archived, and it gets no further releases or security fixes. Never confuse the Ingress API with that retired controller, and do not write a card that presents Ingress NGINX as a current option. Gateway API is released separately from Kubernetes, as CustomResourceDefinitions with their own version numbers: cards about it test the long-standing Standard channel resources (GatewayClass, Gateway, HTTPRoute) and the roles they separate, not route types whose channel changed recently (TCPRoute and UDPRoute moved to the Standard channel only in Gateway API v1.6).
- Outdated study material: the kubernetes.io cloud native security page no longer presents the "4C's of cloud native security" (Cloud, Clusters, Containers, Code); it organises security by the lifecycle phases Develop, Distribute, Deploy and Runtime. Do not write 4C cards. The CNCF TOC restructured its TAGs in 2025 into five: Developer Experience, Infrastructure, Operational Resilience, Security and Compliance, Workloads Foundation; TAG Observability, TAG App Delivery, TAG Runtime, TAG Network, TAG Storage and TAG Security no longer exist under those names. OpenTracing and OpenCensus are archived and merged into OpenTelemetry (the curriculum PDF's boilerplate still names OpenTracing as a hosted project: ignore it), and OpenTelemetry reached graduated status in May 2026. Any card that states a project's maturity level gets "volatility": "may_change" and must be checked on cncf.io/projects today.
- Never state a judgement as a fact. "X is the best way" is acceptable only when an official page says it in those terms (for example the Kubernetes project recommending Gateway API over Ingress). Prefer statements about behaviour.
- Overlap with other decks: cards are about upstream Kubernetes and CNCF, not a cloud provider's managed offering; leave GKE, EKS and AKS specifics to the AWS, Google Cloud and Azure decks (including gcp-ace and aws-dva-c02). Container image building belongs to docker-fundamentals, CI pipelines to github-actions, infrastructure as code to terraform-associate.
