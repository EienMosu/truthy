- Constraint and key traps, verified: a primary key implies NOT NULL and a unique B-tree index; a foreign key requires a primary key, unique constraint or non-partial unique index on the referenced side but creates no index on the referencing columns (the docs call indexing them "often a good idea"); ON DELETE NO ACTION is the default; NO ACTION allows the check to be deferred while RESTRICT does not; by default a referencing row with any null referencing column is not checked, while MATCH FULL still lets a row whose referencing columns are all null escape, so never write that MATCH FULL rejects every null; an identity column is NOT NULL but not unique by itself; serial is not a true type; CHECK constraints are examined only when a row is inserted or updated. Leave out exclusion constraints beyond naming them, deferrable constraint syntax beyond the NO ACTION versus RESTRICT difference, and constraint triggers.
- Index traps, verified: a multicolumn B-tree index can be used with conditions on any subset of its columns and is most efficient with conditions on the leading columns; since PostgreSQL 18, skip scan lets it be used in more cases where leading columns have no condition. So write no card claiming a multicolumn index is unusable without a condition on its first column. The planner chooses between an index and a sequential scan by estimated cost, so no card says a query "always uses" an index; describe what an index makes possible. LIKE 'abc%' can use a B-tree index while LIKE '%abc' cannot, and outside the C locale it needs a pattern operator class (indexes-opclass.html). CREATE INDEX blocks writes but not reads; CONCURRENTLY avoids blocking writes and cannot run inside a transaction block. EXPLAIN ANALYZE executes the statement, so it changes data when used on INSERT, UPDATE, DELETE or MERGE. Leave out index types other than B-tree beyond naming them (Hash, GiST, SP-GiST, GIN, BRIN), the 32-column limit, fillfactor, HOT updates, bloat and REINDEX.
- Transaction and isolation traps, verified on transaction-iso.html: PostgreSQL implements three distinct levels, because Read Uncommitted behaves like Read Committed (no dirty reads at any level); in Read Committed each statement sees data committed before it began, so two SELECTs in one transaction can see different committed data; Repeatable Read sees a snapshot from its first non-transaction-control statement, not from BEGIN, prevents phantom reads in PostgreSQL but still allows serialization anomalies, and raises "could not serialize access due to concurrent update" instead of overwriting a concurrent change; Serializable may raise serialization failures (SQLSTATE 40001) that the application must retry; its predicate locks do not block. Under MVCC, reading rows never blocks writing them and writing never blocks reading; this is about plain SELECT and row writes, because commands that take an ACCESS EXCLUSIVE lock (for example VACUUM FULL or a REFRESH MATERIALIZED VIEW without CONCURRENTLY) can block readers, so no card says nothing ever blocks a SELECT. Row-level locks from SELECT FOR UPDATE block other writers and lockers of the same rows, not plain readers. Sequence values are not rolled back, so identity and serial columns can have gaps. now() and CURRENT_TIMESTAMP stay the same for the whole transaction. Popular material that says Repeatable Read allows phantoms is describing the standard's minimum, not PostgreSQL: a card on this says "In PostgreSQL". Leave out exact lock mode tables, lock conflict matrices, advisory locks, two-phase commit, transaction ID wraparound and autovacuum settings.
- Upsert traps, verified on sql-insert.html: DO UPDATE requires a conflict target while DO NOTHING does not (without one it handles conflicts with all usable constraints and unique indexes); the proposed row is referenced as excluded; only NOT DEFERRABLE constraints and unique indexes can be arbiters, and exclusion constraints cannot be arbiters for DO UPDATE; a single INSERT ... ON CONFLICT DO UPDATE that would affect the same existing row twice raises a cardinality violation error rather than updating twice; the DO UPDATE WHERE condition decides which conflicting rows are updated, though all are locked; the command tag counts rows inserted or updated. ON CONFLICT DO UPDATE guarantees an insert or an update even under high concurrency; sql-merge.html points to INSERT ... ON CONFLICT as the alternative that can update when a concurrent insert occurs and says the two are not interchangeable: never write that they are.
- Data type traps, verified: numeric is exact and recommended for monetary amounts, real and double precision are inexact; numeric rounds ties away from zero and double precision rounds ties to even on most machines (say "on most machines" or leave the double precision side out); 5 / 2 is 2 for integers and (-5) / 2 is -2; there is no performance difference among text, varchar(n) and char(n) apart from char(n) storage and length checks, and the page says char(n) is usually the slowest; an explicit cast to varchar(n) truncates silently while storing an over-length value raises an error unless the excess is spaces; timestamp with time zone does not store a time zone, it converts input to UTC and output to the session TimeZone; the bare word timestamp means timestamp without time zone. Leave out storage sizes, digit limits, the money type, interval arithmetic, date/time input formats and special values beyond NaN and Infinity, arrays, enum types, JSON and jsonb, and the network and geometric types.
