# Truthy native, plan A (shared data and repository integration) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The web repository produces, checks and commits `native-data/`: the 54 decks as the web builds them (with a fixed index version), the design tokens with the code's overrides applied, and golden vectors computed by the TypeScript code for every function the native apps port. Native-only commits neither deploy the web nor run its CI, and the public-repository hygiene rules cover native files.

**Architecture:** Everything that writes `native-data/` lives in `scripts/native/` and runs under Vitest, because many of the functions to export live in React component files (`components/**/*.tsx`) that only Vitest's environment imports cleanly. `scripts/native/export.ts` composes three producers (decks, tokens, golden vectors) into one map of repository-relative paths to file contents. `tests/native-data.test.ts` builds that map and compares it with the committed files (the drift gate); with `UPDATE_NATIVE_DATA=1` (the `pnpm export:native` script) the same test writes the map instead. Golden vector files share one JSON format, defined below, which plans B and C decode.

**Tech Stack:** TypeScript 5.9 (strict, `noUncheckedIndexedAccess`), Vitest 4 with jsdom for component modules, zod 4, Node 24, pnpm 10.34.0, GitHub Actions, Vercel.

**Spec:** `docs/superpowers/specs/2026-10-14-truthy-native-apps-design.md` (binding) and its companion `docs/superpowers/specs/2026-10-14-truthy-native-port-reference.md` (the measured facts: section 3.9 is the inventory of functions to export, section 5.0 the token override table, section 8 the repository rules). Where this plan and the spec disagree, the spec wins; stop and report. The exceptions are the deviations listed under "Deviations from the spec" below: the plan follows those, and an executor does not stop on them.

## Global Constraints

- `native-data/` is generated by `pnpm export:native` and committed; nothing in it is edited by hand. `scripts/native-token-overrides.json` is the only hand-kept native data file.
- Deck files are the web build output, byte for byte, except the index's per-deck `version`, which is the fixed version recorded in `native-data/manifest.json` and changes only when a deck hash changes. Card order inside a deck file is kept.
- Golden vectors cover every function and constant in reference 3.9 except the web-only `entriesBehind` and the browser storage adapter (`browserLocalStorage`). They are computed by running the TypeScript functions, never typed by hand. The export fails if a 3.9 function has no vector file. Names 3.9 mentions that are not separate functions get no file of their own and are pinned through their caller: `canStillFinish` through `searchWithAllRules`, `keepUnreadable` through `createLocalStore`, `cards` and `tally` through `resultCopy`, `wholeSeconds` through `clockText` and `timedLabel`.
- Every `it` of a function's web test file that asserts an exact value is in its vector file at least once (for dealing: the `count`, `avoid`, `before` and `budget` options of `deal` as well as `dealChunk`; for the round: event traces of all four classes, including every Timed clock edge case). A loop inside an `it` (seeds, cut points, positions, pixels) contributes the items its task's rules name: task 5's `SAMPLE = 2` and `ROUND_CHUNKS = 6`, task 6's rule 7, task 7's 10 px `listCue` sweep. The web suites keep the full loops. This reading of spec 4.3 is a recorded deviation (below).
- Running the export twice on the same tree gives byte-identical files.
- `vercel.json` gains exactly `"ignoreCommand": "git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- . ':!ios' ':!android' ':!native-data'"` (checked against Vercel's current documentation in task 10).
- `ci.yml` gains `paths-ignore` for `ios/**` and `android/**` only; `native-data/**` keeps running the web checks.
- The new hygiene rules (em dash in text files, signing files by type, PNG text and EXIF chunks) apply to `ios/`, `android/`, `native-data/` and `docs/superpowers/**/*native*`; UTF-16 run reading applies to every binary file (a recorded deviation, below).
- Commits are authored by `EienMosu` with the noreply address already configured in the clone; messages use the `feat:`, `fix:`, `test:`, `docs:`, `chore:` style, with no co-author or generator lines.
- No em dash (U+2014) in any file this plan writes. No absolute local path, no home-folder layout, no e-mail-shaped string.
- `main` is never pushed by this plan. The branch is `native`; it is pushed only with the owner's approval.

## Deviations from the spec

The spec is binding, and this plan departs from its wording in three places. Each is recorded here for the owner's review of the plan; if the owner rejects one, the plan is changed before it is executed. An executor follows them and does not stop on them.

1. **Where the export lives.** Spec 4.1, 4.3 and reference 8.1 name the writer `scripts/export-native.ts`. This plan puts it at `scripts/native/export.ts`, run by `tests/native-data.test.ts` through `pnpm export:native` (`UPDATE_NATIVE_DATA=1 vitest run tests/native-data.test.ts`). Many of the functions it exports live in React component files that only Vitest's environment imports cleanly, so a `tsx` script cannot run them. The behaviour the spec asks for (one export, the drift test, `pnpm export:native`) is the same.
2. **What "every pinned case" means.** Spec 4.3 asks for every pinned case of a function's web test file. This plan reads that as every `it` that asserts an exact value, at least once, with the loops inside an `it` sampled as the Global Constraints say, so that the vector files stay a few megabytes each (task 5's dealing files are about 4.3 MB, task 6's round files about 4.6 MB). No `it` is dropped: task 6 plays the seeds 77 and 78 test as two traces. The web suites keep running every loop in full.
3. **UTF-16 runs everywhere.** Spec 8 scopes its hygiene additions to `ios/`, `android/`, `native-data/` and the native documents. Task 1 reads UTF-16 runs in every binary file of the repository, which is stricter: a font name record that holds a local path or an address is a leak wherever the font sits. It passes on today's tree.

The manifest follows spec 4.1 without a deviation: `native-data/manifest.json` holds the source hashes (`deckHashes`), the fixed deck index version and a generator version (`generator`), plus `format`, the layout version of `native-data/`.

## Review Focus

1. **A content, token or engine change without a re-export.** Expected: `pnpm test` fails in `tests/native-data.test.ts` and names the first differing file. Task 9 adds a mutation case for each producer (a card text, a token value, an override, an engine constant).
2. **Exporting on a different day with unchanged decks.** Expected: byte-identical `native-data/`, including `decks/index.json`, because the recorded version is kept while deck hashes are unchanged. Task 3 pins this with two runs on different `today` values.
3. **Non-finite and negative-zero numbers in vectors.** `dealChunk`'s `budget = Infinity` (shipped dealing pins) and `lastSeenAt` values that are not finite must survive encoding. Expected: `{"$number": "Infinity"}` and friends, decoded back by the format's own round-trip test. Task 4 owns it.
4. **A push whose last commit is native-only but whose earlier commits touch the web.** Expected: Vercel builds, because the ignore command compares against the previously deployed commit. Task 10 pins the command string and documents the reasoning; the behaviour is checked in a scratch repository with two commits.
5. **A keystore, a PNG with a text chunk, or an em dash added under `ios/` or `android/`.** Expected: `tests/repo-hygiene.test.ts` and the pre-push hook both reject it, while the same em dash in an existing web file outside the native scopes is not reported. Task 1 owns it.

## The golden vector format (the contract with plans B and C)

Every golden file is `native-data/golden/<module>.<function>.json`, where `<module>` is the web module path with `/` replaced by `.` and without the extension (for example `src.engine.deal.dealChunk.json`, `components.FlightPath.pointAt.json`). Constants get files of their own, named after the constant (`src.engine.deal.CHUNK.json`), with one case whose `input` is `null` and whose `output` is the value. One name is an exception: the constant `DEAL` of `src/engine/deal` is `src.engine.deal.DEAL.constant.json`, because `src.engine.deal.DEAL.json` and the function's `src.engine.deal.deal.json` are one file on a file system that ignores case (macOS by default). No other two paths are equal ignoring case; task 4's registry test fails if a new pair appears. The contrast pairs are the constant `contrastPairs` of the module `design/system/tokens` (`design.system.tokens.contrastPairs.json`).

```json
{
  "format": 1,
  "module": "src/engine/deal",
  "function": "dealChunk",
  "source": "src/engine/deal.ts",
  "tests": ["tests/engine/deal-pins-polish.test.ts", "tests/engine/chunks.test.ts"],
  "cards": { "<card id>": { "id": "...", "section": "...", "text": { "en": { "statement": "...", "explanation": "..." } }, "answer": true, "source": { "title": "...", "url": "https://..." }, "difficulty": 1, "appliesTo": "", "conflictGroups": [] } },
  "cases": [
    { "name": "pins: 16-card pool, seed 1, first chunk", "input": { "pool": [{ "$card": "a" }], "history": {}, "rng": { "$rng": { "seed": 1 } }, "dealt": [] }, "output": [{ "$card": "c" }] }
  ]
}
```

Rules, all enforced by the encoder of task 4:
- `format` is `1`. Keys are written in a stable order (the order of the TypeScript object, then the encoder's own keys), with two-space indentation and a final newline.
- `input` holds the function's arguments as a JSON object keyed by the parameter names of the TypeScript signature. A function of no arguments has `input: {}`; a constant has `input: null`.
- Every `Card` object in an input or an output is replaced by `{"$card": "<id>"}`, and the full card goes once into the file's `cards` table. A whole shipped deck in file order may be written `{"$deck": "<deckId>"}`, which means the `cards` array of `native-data/decks/<deckId>.json`.
- An rng argument is `{"$rng": {"seed": <uint32>}}` (a mulberry32 stream from that seed) or `{"$rng": {"values": [<numbers>]}}` (returns the values in order and fails when they run out).
- Numbers JSON cannot carry are tagged: `{"$number": "Infinity"}`, `{"$number": "-Infinity"}`, `{"$number": "NaN"}`, `{"$number": "-0"}`. `undefined` is written by leaving the key out; an `undefined` output is `{"$undefined": true}`.
- A thrown error is `{"$throws": "<message>"}` as the output.
- A `RoundState` in an output is written as its snapshot: the state's own fields with `source` replaced by `"chunks": <source.chunks>` (pool, history and seed are in the case's input), and every card replaced as above.
- Integers stay integers; every other number is the exact double the TypeScript produced (JSON's shortest round-trip form). Natives compare numbers exactly.
- Where a case is a sequence (a round trace), `input` is `{"start": <StartArgs>, "events": [<RoundEvent>...]}` and `output` is the list of snapshots after each event, the first entry being the state `startRound` returned.
- An own key named `__proto__` (a stored progress record, reference 8.1) is an ordinary key; decoders must keep it as data.

Per-shape conventions, part of this contract (each task's Rules section is the full statement):
- (a) A function of a `RoundState` has input `{"start", "events", ...other parameters}`. For `currentCard`, `lastAnswer`, `wrongCount`, `livesLeft`, `isDecided` and `summarise` (`src/engine/round`) the output lists the value after every state, `output[0]` from `startRound` (task 6, rule 3). For every other function (`components/play/*`, the header layouts) the output is the value on the state after the last event (task 8, rule 2).
- (b) A `ReadonlySet` is the array of its ids in insertion order (task 5, rule 6).
- (c) A returned function is an object from probe argument to value: `best` of `resultCopy`, `t` of `streakLayout`, `x` of `trailLayout` (task 8, rules 4 and 5). A curried function is one call with all its arguments in one input: `placementCheck` (task 5, rule 6). The closure `searchOverCap` takes is described by its data `{size, avoid, budget}` (task 5, rule 6).
- (d) An rng that continues after earlier draws is `{"$rng": {"values": [...]}}` (`dealRanked`, `arrange`, `pickAnswer`).
- (e) `createRng` outputs its first draws, and a native draws `output.length` values (task 4, rule 14).
- (f) `createLocalStore` cases are scripts (task 7, rule 4).
- (g) A `modeTable` key in an input replaces the class table for that case (task 7, rule 5).
- (h) `findRoute`, `continueTarget` and `recentDecks` write the id projections of task 7, rule 6.
- (i) `switchTheme` input is `{"choice", "systemDark"}`, its output `{"theme", "stored"}` (task 4, rule 14).
